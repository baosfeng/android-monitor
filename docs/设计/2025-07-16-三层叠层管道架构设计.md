# 三层叠层管道架构设计

> 日期：2025-07-16
> 状态：已批准
> 设计目标：重构 Android 行为监控 App 的事件处理架构，实现每层职责分明、面向接口编程、易扩展、易测试

## 1. 背景与痛点

### 当前架构问题

| 痛点 | 根因 |
|------|------|
| 采集内容不够全面 | `EventCollector` 只收取有限的 extra Map，没有"把所有能拿的信息都拿到"的设计 |
| 事件丢失/服务中断 | `EventCollector` 写入 SQLite 失败则事件彻底丢失，没有多路径冗余 |
| 扩展性差 | 新增一种处理方式（如本地文件备份日志）必须改 `EventCollector` 或 `EventReporter` |
| 导航上下文缺失 | 无法追踪"从哪来到哪去"的用户行为链路 |

### 设计原则

1. **单一职责** — 每个模块只做一件事
2. **面向接口编程** — 模块间交互通过接口契约，不依赖具体实现
3. **易扩展** — 新增功能不修改现有代码
4. **易测试** — 每个模块可独立单元测试

## 2. 整体架构

```
┌─ 采集层 ──────────────────────────────────────────────────────┐
│                                                                │
│  EventSource (interface)                                        │
│    ├─ AccessibilityService        → 前台切换/Activity/通知      │
│    ├─ BroadcastReceiver 群组       → 屏幕/充电/WiFi/蓝牙/...    │
│    └─ (未来新源，只需实现接口)     → 任何来源                    │
│                                                                │
│  NavigationContextTracker                                       │
│    └─ 维护导航上下文栈（"从哪来到哪去"）                        │
│                                                                │
│  RawEventCollector                                              │
│    └─ 从 EventSource + ContextTracker → 组装 RawEvent          │
│    └─ RawEvent 包含：基本信息 + 结构化数据 + 导航上下文 + 设备快照 │
│                                                                │
└──────────────────────────┬──────────────────────────────────────┘
                           │ RawEvent
                           ▼
┌─ 管道层 ───────────────────────────────────────────────────────┐
│                                                                │
│  EventPipeline (interface)                                      │
│    └─ dispatch(rawEvent)                                        │
│    └─ fork 给所有已注册 Handler（独立协程，互不阻塞）            │
│                                                                │
│  register(handler) / unregister(id)   →  运行时动态增删         │
│                                                                │
└────┬───────────────┬───────────────┬────────────────────────────┘
     │               │               │
     ▼               ▼               ▼
┌──────────┐ ┌──────────────┐ ┌────────────┐
│Database  │ │Upload        │ │Log         │  ← 执行层
│Handler   │ │Handler       │ │Handler     │
│          │ │              │ │            │
│SQLite    │ │上传队列→HTTP  │ │Logcat调试  │
│持久化     │ │批量上报        │ │辅助        │
└──────────┘ └──────────────┘ └────────────┘
                                        ↑
                              (未来扩展点)
```

### 分层职责

| 层级 | 职责 | 只做 | 不做 |
|------|------|------|------|
| **采集层** | 事件采集与信息打包 | 获取所有可用信息组装成 RawEvent | 不处理、不存储、不上传 |
| **管道层** | 路由与扇出 | 将 RawEvent 转发给所有已注册 Handler | 不改数据、不过滤、不阻塞 |
| **执行层** | 具体业务处理 | 每个 Handler 独立完成单一职责 | 互不依赖、不跨 Handler 调用 |

### 数据流方向

```
单向：采集层 → 管道层 → 执行层
无反方向依赖，无跨层调用
```

## 3. 采集层设计

### 3.1 EventSource 接口

所有事件源的统一接口——提供原始数据，不关心后续处理：

```kotlin
interface EventSource {
    /** 提供当前事件的原始数据，RawEventCollector 负责组装成 RawEvent */
    fun collectRaw(): RawEventData
}
```

实现者：`MonitorAccessibilityService`、各 `BroadcastReceiver`、未来新增来源。

`RawEventData` 是一个开放的数据容器，EventSource 只负责填充自己能获取到的信息：

```kotlin
data class RawEventData(
    val eventType: EventType,
    val packageName: String?,
    val className: String?,
    val summary: String,
    val interactionDetails: Map<String, String>,
    val screenContent: ScreenContent?,
    val rawExtra: Map<String, String>,
    val structuredData: JsonObject?
)
```

> `RawEventData` 不包含 `deviceId`、`timestampMs`、`navigationContext`、`systemState` 等——这些由 `RawEventCollector` 在组装时自动填充。

### 3.2 RawEvent 数据模型

自包含的完整信息包——所有事件源采集的信息都打包在此：

```kotlin
data class RawEvent(
    val eventType: EventType,
    val timestampMs: Long,
    val deviceId: String,
    val packageName: String?,
    val className: String?,
    val summary: String,
    val interactionDetails: Map<String, String>,
    val screenContent: ScreenContent?,
    val systemState: SystemStateSnapshot?,
    val rawExtra: Map<String, String>,
    val structuredData: JsonObject?,                    // 任意复杂嵌套结构
    val navigationContext: List<ContextFrame>            // 导航上下文栈
)
```

**关键设计点：**
- 字段使用 nullable 类型，采集层只填充能获取到的字段
- `structuredData` 保留原始 JSON 结构，不丢失信息（如公众号文章详情）
- `navigationContext` 记录完整导航链路

### 3.3 NavigationContextTracker

维护导航上下文栈，每次页面切换时记录一帧：

```kotlin
data class ContextFrame(
    val timestampMs: Long,
    val packageName: String,
    val className: String,
    val screenLabel: String,
    val screenDetails: JsonObject?,
    val source: String?
)
```

**追踪示例 — 微信公众号文章阅读：**

```
1. { screenLabel: "聊天主界面", source: null }
2. { screenLabel: "订阅号消息列表", source: "底部导航栏" }
3. { screenLabel: "公众号主页", screenDetails: { accountName: "人民日报" }, source: "点击订阅号消息" }
4. { screenLabel: "公众号文章页", screenDetails: { accountName: "人民日报", articleTitle: "..." }, source: "点击文章标题" }
```

### 3.4 RawEventCollector

采集层入口，负责：
1. 接收事件源的原始数据
2. 获取 `NavigationContextTracker` 的当前上下文
3. 获取 `SystemStateSnapshot`（电池/网络/内存等快照）
4. 获取 `ScreenClassifier` 的识别结果
5. 组装成 `RawEvent`
6. 调用 `EventPipeline.dispatch(rawEvent)`

```kotlin
class RawEventCollector(
    private val pipeline: EventPipeline,
    private val navTracker: NavigationContextTracker
) {
    fun emit(source: EventSource) {
        val rawData = source.collectRaw()
        val event = buildRawEvent(rawData)
        pipeline.dispatch(event)
    }

    private fun buildRawEvent(data: RawEventData): RawEvent = RawEvent(
        eventType = data.eventType,
        timestampMs = System.currentTimeMillis(),
        deviceId = AppUtils.getDeviceId(),
        packageName = data.packageName,
        className = data.className,
        summary = data.summary,
        interactionDetails = data.interactionDetails,
        screenContent = data.screenContent,
        systemState = captureSystemState(),
        rawExtra = data.rawExtra,
        structuredData = data.structuredData,
        navigationContext = navTracker.getCurrentContext()
    )
}
```

## 4. 管道层设计

### 4.1 核心接口

```kotlin
interface EventHandler {
    val id: String
    suspend fun handle(event: RawEvent)
}

interface EventPipeline {
    fun register(handler: EventHandler)
    fun unregister(handlerId: String)
    fun dispatch(event: RawEvent)
}
```

### 4.2 扇出机制

`dispatch()` 的实现：

```
for each handler in handlers:
    scope.launch { handler.handle(rawEvent) }
```

- 每个 Handler 在**独立协程**中运行
- 一个 Handler 失败不影响其他 Handler
- Handler 之间 **无顺序依赖**，不保证执行顺序

### 4.3 注册与生命周期

在 `MonitorApp.onCreate()` 中初始化：

```
fun initPipeline() {
    pipeline.register(DatabaseHandler(...))
    pipeline.register(UploadHandler(...))
    pipeline.register(LogHandler())

    // 未来扩展：再加一行
    // pipeline.register(MyNewHandler())
}
```

## 5. 执行层设计

### 5.1 DatabaseHandler

| 属性 | 值 |
|------|-----|
| 职责 | 只做本地 SQLite 持久化 |
| 依赖 | `DatabaseHelper`（已有） |
| 行为 | `RawEvent` → `EventEntity` → `db.insert()` |

### 5.2 UploadHandler

| 属性 | 值 |
|------|-----|
| 职责 | 只做批量 HTTP 上报 |
| 依赖 | `UploadQueue`（新增，封装缓冲+批量逻辑）+ `ApiService`（已有） |
| 行为 | `RawEvent` → 入上传队列 → 缓冲到阈值 → HTTP POST |

### 5.3 LogHandler

| 属性 | 值 |
|------|-----|
| 职责 | 只做调试日志输出 |
| 依赖 | 无 |
| 行为 | `RawEvent` → Logcat |

### 5.4 新增 Handler 的规范

新增一个 Handler 只需三步：
1. 创建类实现 `EventHandler` 接口
2. 在 `initPipeline()` 中注册
3. 无需改任何现有代码

## 6. 模块依赖关系

```
MonitorApp.onCreate()
    └─ initPipeline()
         ├─ 创建 RawEventCollector
         ├─ 创建 EventPipelineImpl
         ├─ 注册 DatabaseHandler → 依赖 DatabaseHelper
         ├─ 注册 UploadHandler  → 依赖 UploadQueue + ApiService
         ├─ 注册 LogHandler     → 无依赖
         └─ 将 pipeline 注入 RawEventCollector

数据流方向：采集层 → 管道层 → 执行层（单向，无反向依赖）
```

### 包结构（新增）

```
com.bsfeng.monitor.pipeline/
    ├── EventSource.kt          // EventSource 接口 + RawEventData 数据类
    ├── RawEvent.kt             // RawEvent + ContextFrame + SystemStateSnapshot 数据模型
    ├── EventHandler.kt         // Handler 接口
    ├── EventPipeline.kt        // 管道接口 + 默认实现
    ├── RawEventCollector.kt    // 采集层入口
    ├── NavigationContextTracker.kt  // 导航上下文追踪器
    └── handler/
        ├── DatabaseHandler.kt
        ├── UploadHandler.kt
        └── LogHandler.kt
```

## 7. 迁移路径

| 阶段 | 内容 | 影响范围 | 验证方式 |
|------|------|---------|---------|
| **Phase 1** | 新增 `pipeline` 包：`RawEvent` + 接口定义 + `EventPipelineImpl` | 纯新增，0 影响 | 编译通过 |
| **Phase 2** | 实现 `NavigationContextTracker` + `RawEventCollector` | 新增代码，旧 `EventCollector` 保留过渡 | 单元测试 |
| **Phase 3** | 逐个迁移事件源到新采集入口 | 逐步替换 `EventCollector.emit()` | 运行时比对 |
| **Phase 4** | Handler 逐个就位：`LogHandler` → `DatabaseHandler` → `UploadHandler` | 每步可独立测试 | 功能测试 |
| **Phase 5** | 移除旧的 `EventCollector` 单例，清理过渡代码 | 删除文件 | 编译+回归测试 |

> 全程可灰度切换：新旧两条路径并存，比对数据一致性后再完全切换。

## 8. 测试策略

| 层级 | 测试方式 | 测试重点 |
|------|---------|---------|
| **采集层** | 单元测试 | `RawEventCollector` 是否正确组装 `RawEvent`；`NavigationContextTracker` 入栈/回退逻辑 |
| **管道层** | 单元测试 | `EventPipeline` 是否正确 fork 给所有 Handler；异常场景不影响其他 Handler |
| **执行层** | 单元测试 | 每个 Handler 独立测试，Mock `RawEvent` 断言行为 |
