# 提交规范

## 提交信息格式

```
<type>: <中文描述>
```

## 允许的 type

| Type | 使用场景 |
|------|---------|
| `feat` | 新增功能或文档 |
| `fix` | 修正错误或过时内容 |
| `docs` | 纯文档更新 |
| `refactor` | 重构文档结构或组织方式 |
| `test` | 添加或更新测试 |
| `chore` | 构建、配置等杂项变更 |

## 示例

```
feat: 添加事件上报模块

fix: 修正屏幕分类器包名识别逻辑

docs: 更新事件类型定义文档
```

> **注意：** 提交信息必须使用中文描述，type 保持英文小写。

## 开发流程要求

```
① 先写文档 → ② 再写代码 → ③ 写测试用例 → ④ 运行测试验证 → ⑤ 打包 APK → ⑥ 安装到手机验证
```

- **文档先行：** 任何功能开发前，必须先编写设计文档或接口说明
- **新增代码必须添加测试用例：** 每新增一个类/方法/功能，必须同时添加对应的单元测试，覆盖正常路径、边界条件和异常场景
- **运行测试验证：** 编码完成后必须运行 `./gradlew test`，确保全部通过
- **测试失败必须修复：** 不管失败是否是本次改动导致的，都要排查修复，不得推诿
- **编译通过后打包 APK：** 每次编译通过后必须运行 `./gradlew assembleDebug` 生成 APK
- **提交前必须确保所有测试通过**

## 提交策略

### 每功能一提交

> **每完成一个功能就单独提交一次，不攒批提交。**

- 只要一个独立改动（含测试）完成并通过验证，就可以立即提交
- 不必等到所有改动一起完成再提交
- 每个提交应是可验证、可独立运作的原子变更，便于回滚和 Code Review
- 提交信息应清晰说明改了什么以及对应的测试覆盖

### 提交信息示例

```
feat: 添加事件上报模块

fix: 修正屏幕分类器包名识别逻辑

docs: 更新事件类型定义文档

test: 为 EventCollector 添加单元测试
```

## 临时文件规则

计划和任务类临时文档（无论来源）为临时文件，不得纳入 git 跟踪或提交，任务完成后会被自动删除。

## 每次改动交付要求

每次代码改动完成后，必须：
1. 运行 `./gradlew test` 确保所有测试通过
2. 运行 `./gradlew assembleDebug` 编译 Debug APK
3. 将生成的 `app/build/outputs/apk/debug/app-debug.apk` 安装到手机验证：`adb install -r <apk路径>`
4. 确认功能正常后提交代码
