# 数据备份与还原

> 结论：App 把两张库的**一致快照** + 白名单偏好 + 两个白名单文件打成 zip，**只落 App 私有目录**（不写公共 Downloads），包内定位坐标降到 3 位小数；设置页可立即备份、按天/周自动备份，也可从 zip 还原（还原前自动留一份 pre-restore 包）。

## 备份内容

归档根 = 应用私有数据目录 `dataDir`，包内保持相对路径，只收三类：

- **两个库**：`databases/finance.db`、`databases/monitor.db`，以及快照时仍非空的 `-wal`（checkpoint 成功后它通常是 0 字节，不进包）
- **白名单 prefs**（`shared_prefs/` 下只有这些 `.xml` 进包）：`monitor_appearance`、`feature_flags`、`skip_config`、`skip_rule_prefs`、`skip_whitelist`、`backup_prefs`、`widget_prefs`、`trip_map`、`quota_settings`、`quota_alerts`、`quota_snapshots`、`autobook_ignored`、`totp_settings`、`finance_prefs`
- **`files/` 下两个白名单文件**：`skip_rules_v1_backup.json`、`profileInstalled`（存在才加）

外加 `manifest.json`：schemaVersion、appVersionName、createdAt、每个文件的 size + sha256、两张库的表行数。

### 一致快照（打包前必做）

- 每个库在**同一连接上的写事务**（`BEGIN EXCLUSIVE`）内复制主库与 `-wal`：从 `beginTransaction` 到 `endTransaction` 之间没有任何提交能落盘，包内的「主库 + wal」因此是 SQLite 认可的一组合。事务本身不写数据、结束即回滚，库内容零改动。
- 表行数在**同一个冻结窗口内**统计，与这份快照严格对应；还原后拿它自检（包内实际行数 ≠ 清单登记值即为不一致）。
- 拿不到写闸（重试 3 次仍 `SQLITE_BUSY`）→ **本次备份失败**。宁可让用户重试，也不产出「看起来正常、还原后少若干条」的包。
- `-shm` 不进包：它是 WAL 的内存索引，还原端会删掉重建。
- 旧实现依次用三个 `FileInputStream` 读 db → wal → shm，全程不加锁，遇到并发写就是「旧主库 + 空 wal」，还原后静默丢最近记录 —— 这是本条规则的反例。

### 定位坐标降精度

本机库保留 6 位小数（≈0.11m，轨迹要能画出几十米移动）；**备份包里降到 3 位（≈110m）**。只改 `records` 表里 `action = COORDINATE` 的 detail，其它行原文不动；降精度失败只记 W 日志、按原精度打包（包已不出私有目录，可用性优先于这一步加固）。

## 存储双模式

- 默认 `LOCAL`：现有私有目录与 5 份保留；`SERVER`：同一份 zip 上传服务器，保留由服务端执行。
- 切换模式不迁移、不删除另一端备份；恢复仍走本页流水线，服务端只提供字节。
- 契约见 [存储模式概述](../存储模式/概述.md) 与 [服务器存储 API](../网络通信/服务器存储API.md)。

## 存放位置

- `Android/data/<包名>/files/backups/monitor-backup-yyyyMMdd-HHmmss.zip`：**唯一的自动落点**，也是还原入口与「共 N 份」的快速列表来源。**卸载 App 即消失**（设置页「立即备份」行副标题照此写）。
- **备份不自动写公共 `Downloads/行为记录备份/`**：不加密的包（真实账目 + 使用记录 + 轨迹坐标）落在公共目录等于对同机任何文件管理器与网盘同步敞开，用户还无从知晓。
- 要搬出设备走**显式导出**：设置 → 数据与备份 →「导出到下载目录」→ 挑一份 → 破坏性确认（文案点明包未加密）→ 复制一份到 `Downloads/行为记录备份/`。原文件保留，不自动、不定时，不做批量。
- **还原不受影响**：SAF 选择器（`OpenDocument`）本来就是全盘可选，Downloads 里那份 zip 直接能选；「共 N 份」只统计私有目录，与导出无关。
- 历史版本可能已在 Downloads 留下明文包；App 不自动删用户可见文件，请手动删除该目录。
- 普通备份最多保留 5 份，超额删最旧；pre-restore 回滚包用独立前缀、只留 2 份，不占用这 5 份配额。

## 频率

- 关闭 / 每天 / 每周，默认每周（5 份配额约覆盖一个月，够回滚「上周改错账目」）。
- 用 AlarmManager `setInexactRepeating`（requestCode 7301，与保活心跳的 0 分开），不引入 WorkManager；开机后由 `AlarmReceiver` 心跳调 `ensureScheduled` 补排，已在跑时不重置触发时间。
- 系统省电策略会推迟触发时间（inexact 语义属正常）；关键节点（换签名、重装前）优先手动「立即备份」。

## 还原路径

设置页 →「数据与备份」→「从备份还原」→ SAF 选 zip，顺序固定：

1. 校验 manifest（结构版本、文件清单、非法路径）与每个文件的 size + sha256；
2. 自动把当前数据备份成 pre-restore 包（这一步失败即中止，现有数据不动）；
3. `close()` 两个数据库单例句柄，清掉旧 `-wal`/`-shm`/`-journal`，再逐个文件「同目录临时文件 → 原子 rename」替换；
4. 结束进程（`Process.killProcess(Process.myPid())`），用户重新打开 App 时连接按新文件重建。

替换开始前先原子写 `files/restore.marker`（记录 pre-restore 包名），全部替换成功后才删。第 3 步中途断电/被杀，下次启动 `MonitorApp.onCreate` 检测到 marker 就用 pre-restore 包自动回滚并清 marker。

Android 10+ 对「从后台拉起自身界面」有限制，这里不强行 startActivity，重启后从桌面点开即可。

## 还原失败怎么办

- 文件替换中途中断，库打不开：下次启动自动用 pre-restore 包回滚；回滚包找不到时从 `files/backups/` 挑上一份手动还原。
- 包损坏 / 校验不过：本机留有多份备份，互相替补。
- 还原后数据不是预期版本：换正确的 zip 重来；pre-restore 回滚包单独保留最近 2 份。

## 数据库连接要求

- 备份只读计数 + checkpoint，不改数据；还原必须先 `close()` 单例 helper 再替换文件。
- 兜底口径：句柄关不掉时按「替换文件后立即结束进程」处理——代价是关闭瞬间的内存缓冲未落盘，可能丢最后一次写入，用 pre-restore 包恢复。
