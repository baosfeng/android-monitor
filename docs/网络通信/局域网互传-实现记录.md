## 4. 两条互操作链路（与 Mac 端已对齐，负责人 2026-10-18 确认）

### 4.1 接收端生成 pairingKey → approved 响应下发 → 发送端持久化

```
Mac(发送)                          Android(接收，本端)
  POST /offer  (无 X-Pair-Key，无 pin)
                    ───────────▶  生成 PIN=1234，state=pending，token 照常返回
                    ◀───────────  data={sessionId, token, state:"pending", accepted:[]}
  POST /offer  (body 带 pin:"1234", 可带 sessionId)
                    ───────────▶  校验 PIN → settings.savePairingKey(senderDeviceId, key)
                                  （key = 32 字节随机 hex，SecureRandom）
                    ◀───────────  data={sessionId, token, state:"approved",
                                        accepted:[{fileId, offset}], pairingKey:"<64 hex>"}
  设置端持久化 pairingKey（按 deviceId）
  之后 POST /offer 带 X-Pair-Key: <key> ▶ 接收端 compare == settings.pairingKey(deviceId)
                                         ▶ 直接 approved（免 PIN）
```

实现要点：
- 生成/比较：`TransferEngine.offer()`；持久化：`TransferSettings.savePairingKey()`。
- 下发字段只在**新配对成立的 approved 响应**里出现（`pairingKey`），pending/denied 不带；老客户端忽略该字段即可继续走 PIN。
- 发送端读取：`TransferEngine.sendFilesInternal()` / `submitPin()` 中 `api.string("pairingKey")` → `settings.savePairingKey(peer.deviceId, …)`。
- 移除配对：`TransferEngine.removePairing()` → 「传送」页设备行「移除配对」。

### 4.2 重提 PIN 时的会话复用判定

优先级（`TransferEngine.offer()` 内）：

1. body 带 `sessionId` 且 `sessions[sessionId].senderDeviceId == senderDeviceId` → 复用该会话；
2. 否则按 `senderDeviceId` 相同 + `files.sha256` 集合相同 + 会话非终态 → 复用（容忍对端不回传 sessionId）；
3. 否则新建会话（新 `sessionId` + 新 token，并登记 RECV 任务）。

复用后的 approve 会把已存在的 `.part` 长度作为 `offset` 回填（协议 §6 续传），因此**重提 PIN 不会重传已收字节**。

### 4.3 续传偏移的唯一来源：`.part` 实际大小（重启场景）

`TransferEngine.resumableOffset(incoming)` 是**唯一**偏移来源（`.part` 不存在→0；长度 ≤ 声明大小→该长度；超长→视脏数据删除后按 0；已收满→返回 size）。三处复用：

| 复用点 | 作用 |
|--------|------|
| `acceptedArray()`（`/offer` approved 与 `/offer/status`） | 应答 `accepted[].offset` |
| `approve()` | 回填 `incoming.received` 并写回任务进度 |
| `upload()` 入口 | 严格校验 `offset`（不匹配仍返回 4003） |

与 Mac 端 `TransferService+Offer.swift` 的 `UploadPlanner.resumableOffset(partSize:expectedSize:)` 同源。修复前用内存 `received`：接收端进程被系统回收重启后内存为 0、磁盘 `.part` 有 5 字节 → 应答 `offset=0` → 发送端从头传 → 4003 → 续传失效。
