## 1. 结论速览（TL;DR）

| # | 结论 | 证据 |
|---|------|------|
| 1 | 无 Root 环境下，**通知监听（NLS）+ 无障碍读屏** 是仅有的两条可行通道；最准的那条（Hook 微信/支付宝进程内数据）需要 Xposed/Root | [AutoAccounting README 工作模式表](https://github.com/AutoAccountingOrg/AutoAccounting) |
| 2 | **微信 8.0.52+ 对无障碍服务做了白名单校验**（只校验无障碍服务完整 ID 的**后半段类名**，不校验包名），非白名单服务拿不到微信节点 | AutoJs6 issue [#463](https://github.com/SuperMonster003/AutoJs6/issues/463) 作者 SuperMonster003 原话 + 评论区 |
| 3 | 同一 issue 下有开发者反馈：**「无障碍读取微信和支付宝账单详情，支付宝可以正常读取，微信不行」** —— 与本项目实测完全一致 | 同上，评论者 SunnyHerry |
| 4 | 真机实测（本项目，小米 14）：**支付宝账单详情页无障碍树完全可读**，一次 dump 拿到 95 个节点，金额/时间/付款方式/收款方/分类全都在 | `adb shell uiautomator dump`，见 §4.1 |
| 5 | 支付宝详情页节点**几乎没有 resource-id**（95 个节点里 0 个可用 id），因此识别只能走「文本 + 坐标」而不是 selector | 同上 dump 原文 |
| 6 | 支付详情页是「左标签 + 右值」的表格布局，**同一行两个节点 Y 坐标对齐**（`收款方全称`[75,1349] / `阿里云计算有限公司`[375,1346]），按 Y 分行即可稳定取值 | 同上 dump 原文 |
| 7 | 主流开源方案的规则维护成本极高：AutoAccounting 规则库 **319 条规则 / 31 个 App**，且自 v0.5.7 起**规则更新改为付费**；其规则提交仓库有 **745 个适配 issue** | [rules.md](https://github.com/AutoAccountingOrg/AutoRuleSubmit/blob/main/rules.md) + issue 列表 + issue #795 评论 |
| 8 | 微信支付在其规则库里**一条规则都没有** —— 微信的数据靠硬编码 Hook（`WechatHooker` 等），说明微信页面本身不适合规则化 | rules.md 中 `## com.tencent.mm` 段为空 |
| 9 | 无 Root 方案必须「宁可漏记不可记错」：主流实现都把**未来时态**（将于/即将/待扣/续费提醒）与**提现/充值**（账户间转移）直接放弃 | blue-whale `FUTURE_MARKERS`、seamless README 已知限制 |
| 10 | 本项目选择：**无障碍识别 + 浮窗确认**（不自动落库），把「识别不确定性」交还给用户一次点击 | `.open-design/23-autobook-styles.html` 原型 + 本节 §6 |

## 2. 业界五条采集通道对比

| 通道 | 原理 | 准确率 | 适配成本 | 无 Root 可用 | 代表实现 |
|------|------|--------|---------|-------------|---------|
| **通知监听**（NotificationListenerService） | 读系统通知的 title/text/bigText | 中（受通知文案与是否发通知影响） | 低（正则） | ✅ | [SmartLedger](https://github.com/huanghhcri/SmartLedger)、[blue-whale-keeper](https://github.com/a2244921700-code/blue-whale-keeper) |
| **无障碍读屏** | 解析支付结果页节点树 | 中高（页面在就能读） | 中（页面改版要调） | ✅ | 本项目、[moji-android](https://github.com/helh1723-lang/moji-android) |
| **Xposed / LSPatch Hook** | 直接 Hook 微信/支付宝进程内方法，拿原始交易 JSON | **最高**（原始数据） | 高（要跟版本） | ❌ 需 Root/LSPatch | [AutoAccounting](https://github.com/AutoAccountingOrg/AutoAccounting) |
| **OCR 截图识别** | 无障碍截图 + OCR（PP-OCRv5 ncnn） | 中（受截图时机/字体影响） | 中 | ✅ | AutoAccounting OCR 模式、本项目后续可选 |
| **短信** | 读银行/支付短信 | 中（仅银行渠道） | 低 | ✅ | [Dinecost](https://github.com/Muyizii/Dinecost) |

> **取舍**：本项目已有现成的无障碍服务与选择器基础设施，且用户明确要「无障碍自动记账」，因此以**无障碍读屏**为主通道；通知通道作为后续补充（可覆盖微信无障碍拿不到的场景）。

## 3. 深度案例：AutoAccounting（947★，最成熟的同类项目）

### 3.1 架构：它不是「记账 App」，而是「账单采集插件」

README 明确：「自动记账是一个**账单信息采集插件**，需要配合专业记账软件使用」——采集后写入钱迹/一木/小星/一羽的数据库（`xposed/hooks/qianji/` 下有整套钱迹 DB hook）。

三种工作模式：**LSPosed（Xposed）** / **LSPatch** / **OCR 模式（无障碍 / Shizuku 截图）**。

### 3.2 采集通道与触发方式（源码事实）

| 通道 | 实现文件 | 关键做法 |
|------|---------|---------|
| 通知 | `app/src/main/java/net/ankio/auto/service/NotificationService.kt` | `onNotificationPosted` 取 `EXTRA_TITLE` + (`EXTRA_BIG_TEXT` ?: `EXTRA_TEXT`) → 白名单包名 → 关键词白/黑名单 → 交给规则引擎 |
| 微信 | `.../xposed/hooks/wechat/hooks/WebViewHooker.kt` | Hook `com.tencent.xweb.WebView.evaluateJavascript`，匹配 `nativeWXPayCgiTunnel:ok`，从 `WeixinJSBridge._handleMessageFromWeixin` 的 `respbuf` 解析出**支付 CGI 原始 JSON**（含 fee/nickname/转账单号/时间），删 `entrances` 后 MD5 去重 |
| 支付宝 | `.../xposed/hooks/alipay/hooks/WebViewHooker.kt` | 识别账单页（URL 含 `tradeNo=` 且脚本含 `window.ALIPAYVIEWAPPEARED=1`）→ 注入 JS 劫持 `AlipayJSBridge.call` → 轮询取回 RPC 结果 JSON |
| 短信 | `.../service/SmsReceiver.kt` + `xposed/hooks/sms/` | 读银行/支付短信 |
| OCR | `.../service/ocr/` + `ocr/src/main/java/net/ankio/ocr/OcrProcessor.kt` | PP-OCRv5 ncnn；`PageSignature`（包名+Activity+结构指纹）记住页面以便下次自动触发 |

### 3.3 规则引擎（最值得借鉴的部分）

- 规则 = **JS 脚本**，存数据库 `RuleModel`（字段：`app` / `type` / `js` / `name` / `creator` / `autoRecord` / `enabled`）
- 运行时按 `app + type(DATA/NOTICE/OCR)` 装载规则，用 **QuickJS**（`quickjs-android`）拼成一段可执行 JS：注入 `common.js` + 各规则 + 遍历逻辑
- 每条规则导出 `rule_N.get(data)`，返回含 `money` 的对象即命中（见 `server/src/main/java/org/ezbook/server/engine/RuleGenerator.kt`）
- **规则契约**（issue 回复中的真实输出）：
  ```javascript
  { type:'Transfer', money:5, fee:0, shopName:'…', shopItem:'…',
    accountNameFrom:'支付宝基金付款账户', accountNameTo:'支付宝基金',
    currency:'CNY', time:1791779917000, channel:'支付宝[基金-收入]', total:0 }
  ```
- 规则可云端更新（`app/src/main/java/net/ankio/auto/update/RuleUpdateHelper.kt`，从 `license.ez-book.org` 下载 zip），**自 v0.5.7 起改为付费**

### 3.4 账单数据模型（`BillInfoModel`）

值得借鉴的字段设计：`type`(Income/Expend/Transfer) / `money`(恒正) / `fee`(负=手续费，正=优惠) / `shopName` / `shopItem` / `cateName` / `accountNameFrom` / `accountNameTo` / `app` / `channel` / **`groupId`（短时间内同额合并的去重 id）** / `state` / `auto` / `ruleName`。

去重与合并：`server/src/main/java/org/ezbook/server/tools/BillMerger.kt` —— 账户名按「在已知资产列表中 > 名字更长（更具体） > 保留原值」三层优先挑选。

## 4. 真机实测：支付宝支付页到底能不能读

### 4.1 实测方法与结果（2026-10-16，小米 14 / HyperOS）

```bash
~/android-platform-tools/adb shell uiautomator dump /sdcard/ab.xml
~/android-platform-tools/adb shell cat /sdcard/ab.xml
```

支付宝「账单详情」页（`com.alipay.mobile.nebulax.xriver.activity.XRiverActivity`）**95 个节点全部可读**，关键文本：

| 页面文本 | 节点类型 | 用途 |
|---------|---------|------|
| `阿里云` | TextView | 商户简称（居中标题） |
| `支出3元` | View | **金额 + 方向**（同一串里都有） |
| `交易成功` | TextView | 页面特征词 |
| `支付时间` `2026-10-15 23:14:43` | View ×2 | 时间（同行，Y 对齐） |
| `付款方式` `余额宝` | View + Button | 支付方式 |
| `收款方全称` `阿里云计算有限公司` | View ×2 | 商户全称 |
| `账单分类` `日用百货` | TextView + Button | 平台分类（可直接映射成我们的分类） |
| `商品说明` `充值:阿里云服务购买,业务交易号:CFP000000000000000000` | View | 订单号来源 |

**结论：支付宝侧无障碍方案成立**，且页面自带分类与订单号，识别质量高于通知通道。

### 4.2 微信侧的限制

微信 8.0.52+ 起对无障碍服务做了白名单校验（同上 §1 结论 2）。社区已知的绕过方式是**把自己的无障碍服务类名伪装成白名单内的名字**（典型 `com.google.android.accessibility.selecttospeak.SelectToSpeakService`）：

- AutoAccounting 正是这么做的 —— 它把 `SelectToSpeakService` 的源码复制进自己包里（`app/src/main/java/com/google/android/accessibility/selecttospeak/SelectToSpeakService.kt`），既拿 `takeScreenshot()` 能力，也顺带匹配了微信白名单；
- AutoJs6 作者明确拒绝这种做法，并判断「微信未来很可能加上包名校验，这类方法都会失效」。

> **本项目决策**：**不做类名伪装**（违反平台意图、随时失效、也容易被判定为恶意行为）。微信侧优先走已可用的页面（实测微信首页节点可读，239 节点 / 154 个 resource-id），若支付凭证页确实拿不到节点，则后续补**通知通道**覆盖。

## 5. 通知通道要点（供后续接入时参考）

来自对 12 个开源 NLS 记账项目的源码调研（`bookkeeping` / `SmartLedger` / `blue-whale-keeper` / `WhereIsMyMoney` 等）：

1. **没有一家只读 `EXTRA_TEXT`**：正确顺序是 `TITLE → TEXT → BIG_TEXT → TEXT_LINES[] → SUB_TEXT → SUMMARY_TEXT → "android.infoText" → tickerText`，并按「包含关系去重、保留更长者」（真机上 `title == text == bigText` 会让同一串数字被解析两次）。
2. **金额按来源选锚点**：微信通知必带 `¥`；支付宝标准句式是「你有一笔X元的支出」；银行写「人民币」（卡号不会带这个锚点，天然排除）。
3. **方向判定前必须清洗品牌名**：把 `支付宝/微信支付/云闪付/财付通` 替换成占位符，否则「支付宝 | 20.00元」会因为「支付」二字被判成支出。
4. **必须放弃的文本**：未来时态（将于/即将/明日/待扣/续费提醒）、提现/充值（账户间转移）、无金额的「你有一笔交易，点此查看详情」。
5. **去重窗口**：普通渠道 60s，银行渠道放宽到 600s；用「同额同向 + 商户名互斥」判重并**融合补全**（新证据有商户、旧记录没有 → 更新旧记录而不是新建）。指纹**不要加 UNIQUE 约束** —— 会把「同一分钟两笔同额同商户的真实消费」静默吞掉。
6. **已知硬缺口**：微信扫码收款自 2020 起不再发系统通知（NLS 抓不到）；支付宝转账入账通知不含金额；国产 ROM 杀后台、覆盖安装后通知使用权被系统撤销。

## 6. 本项目方案

### 6.1 交互设计（已确认）

**识别到 → 弹浮窗 → 用户确认 → 落库**，不做静默自动记账。理由：
- 无障碍识别的字段存在不确定性（金额可能取错、商户可能为空），静默落库会污染账本；
- 浮窗一次点击的成本远低于事后发现记错的排查成本。

浮窗内容（见原型）：来源胶囊（支付宝/微信）→ 金额 → 商户 → **类型（可改：支出/收入/转账）** → **分类（可改）** → 账户 / 支付方式 / 时间 → 「忽略」/「记一笔」。

### 6.2 视觉：跟随 App 主题

浮窗所有颜色/圆角/间距都走设计 token（`LocalDesignTokens` + `MonitorTheme`），因此**自动跟随用户在设置里选的 8 套主题**，不写死任何色值。主题对照见 `.open-design/24-autobook-themes.html`。

### 6.3 识别策略

页面特征词命中（`交易成功` / `账单详情` / `支付成功` …）→ 按 **Y 坐标分行**合成「标签 值」行 → 纯文本解析：

| 字段 | 取值方式 | 兜底 |
|------|---------|------|
| 金额 | 带方向前缀（`支出3元`）> 带 `¥` > 带 `元` > 裸两位小数 | 无金额则不弹窗 |
| 方向 | 金额行自带方向词 > 收入词 > 支出词（**先清洗品牌名**） | 默认支出 |
| 商户 | `收款方全称/商户全称/…` 标签同行右侧 | 页面靠前的可用短文本；再取不到留空 |
| 分类 | 平台自带分类（`日用百货`→日用）优先 | 商户关键词；再兜底「其他」 |
| 账户 | 固定用 App 账户体系（支付宝 / 微信钱包） | 规则里配置 |
| 支付方式 | `付款方式/支付方式` 标签值（余额宝/零钱） | 空则不展示 |
| 幂等键 | 有订单号用订单号 | 渠道+方向+金额+商户+5 分钟桶 |

**不记的情况**：无金额、提现/充值、未来时态、命中排除词（账单统计/收支分析/年度账单）。

## 7. 闭源主流 App 是怎么做的（钱迹 / 一木）

| App | 所需权限 | 触发方式 | 官方对准确率的自述 |
|-----|---------|---------|------------------|
| 钱迹 | 无障碍 + 通知 + 悬浮窗 + **忽略电池优化（列为必选）**；可选 adb 授 `WRITE_SECURE_SETTINGS` 做自愈 | 无障碍识别支付页 / 账单详情页 | 「会存在一定概率无法触发的情况……请务必仔细体验后再决定是否为此功能开通会员」 |
| 一木记账 | 无障碍 + 通知栏 + 悬浮窗 | 支付完成**瞬间** 或 进入历史账单详情页 | 「仅是辅助记账的一种手段，请不要过于理想化」「无法保证任何系统任何设备都能够长期稳定运行」 |
| 一木/钱迹 iOS | 快捷指令 + Vision 提取文本 + 剪贴板 | **手动**：轻点/双击背面 | iOS 无「后台自动」，只能 OCR + 手动触发 |
| 钱迹 鸿蒙 | 闪控球 | **手动**点击悬浮球 | 官方承认「应用无法在后台自动获取屏幕内容」 |

**两家都明确承认的失效场景**（对本项目预期管理很重要）：

- **淘宝完全无法识别**：「淘宝主动屏蔽了无障碍的处理，导致无法得到无障碍的回调，目前无法解决」
- 微信**发红包**需要发完再点开红包才能识别；微信**双开**会导致无障碍触发不稳定
- **系统「支付保护」会压制悬浮窗**：小米需关「支付安全检测 / 支付保险箱」，vivo 在 i 管家，华为「支付保护中心」
- 「部分识别场景可能会随着第三方软件的更新而彻底无法正常使用」（一木明确因此不退款）

> **结论**：这个品类的头部产品都在文档里主动劝退，原因是外部的（第三方可随时屏蔽/改版）。**「弹窗让用户确认」正是它们共用的兜底形态，也是本项目的选择** —— 不是实现不完整，而是这个场景的通用解法。

## 8. 稳定的第二通道：官方账单导入

不依赖任何运行时权限、不受 ROM 保活影响，是自动记账失效时的对账兜底。格式要点（来自两个独立开源解析器的源码交叉验证）：

| | 微信 | 支付宝 |
|---|---|---|
| 编码 | UTF-8 | **GB18030**（失败回退 UTF-8，乱码判定：替换字符占比 > 10%） |
| 表头前无效行 | 跳 17 行 | 跳 22 行 |
| 关键列 | 交易时间 / 交易类型 / 交易对方 / 商品 / **收·支**（收入·支出·`/`=不计收支）/ 金额(元) / 支付方式 / 当前状态 / 交易单号 / 商户单号 / 备注 | 交易时间 / 交易分类 / 交易对方 / 对方账号 / 商品说明 / **收·支**（含「不计收支」）/ 金额 / 收·付款方式 / 交易状态 / 交易订单号 / 商家订单号 / 备注 |
| 已知布局 | — | 有「简版 8 列」与「长版 12 列」两种 |

实现建议（比硬编码行号更抗漂移）：

1. **表头定位**：扫描「第一行能解析出时间的记录」作为数据首行，其上一行为表头；或按表头关键词（`交易时间`+`交易类型`+`交易对方`）定位。
2. **表头别名表**：`金额 / 金额(元) / 金额（元）`、`收/付款方式 / 支付方式 / 收/付方式`、`交易对方 / 对方 / 对方账号` 等要同时接受。
3. **退款关联**：支付宝退款单的「交易订单号」是**原单号的前缀**且金额相等 → 两行应标记为同一笔，否则退款会被当新交易重复入账；「交易关闭」+「不计收支」直接判废。
4. **去重口径**：主键用「渠道 + 交易单号」；兜底用「**金额相同 + 时间差 ≤ 1 分钟**」（一木官方文档口径）；跨源（微信账单 + 银行卡账单是同一笔）只能用金额 + 时间窗。
5. **解压密码的坑**：微信/支付宝导出账单的 zip 解压密码是通过 **App 内通知消息**下发的，不在邮件里。

## 9. 合规与上架约束

| 约束 | 内容 | 对本项目的含义 |
|------|------|--------------|
| **Android 13 侧载受限设置** | 侧载安装的 App 申请无障碍权限会被系统拦为「受限制的应用」 | 本项目走 APK 侧载分发，**首次开启无障碍必须引导用户去「允许受限制的设置」** |
| Google Play 无障碍政策 | 非残障用途必须做 Play Console 无障碍声明 + prominent disclosure + demo video + 论证「无更窄 API 可实现」；有开发者因之被连续拒绝 4 次后移除无障碍才上架 | **Play 版本建议只保留「账单导入 + 手动记账」**；无障碍自动记账走国内渠道/侧载 |
| Android 15 通知加固 | 官方只对**检测到 OTP（验证码）的通知**做脱敏；**没有任何官方文本说支付通知金额会被脱敏** | 通知通道仍可用；但截屏/投屏时通知内容会整体隐藏 |
| Android 16 a11y 变更 | 只弃用 `announceForAccessibility` / `TYPE_ANNOUNCEMENT` 播报类 API | **与「读取节点做记账」无关**，不要误判为封杀无障碍抓屏 |
