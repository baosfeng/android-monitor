# 支付宝 / 微信账单导入

> 阅读时机：改账单导入（解析 / 去重 / 分类推断 / 导入 UI）时。关联：[记账概述](概述.md) · [分类体系设计](分类体系设计.md) · [自动记账](自动记账.md)

## 一句话

把支付宝、微信导出的账单文件导入账本：**同一笔以交易单号为身份，已存在则补全、不存在则插入**；分类按「平台分类 > 商品关键词 > 交易对方关键词 > 兜底」自动推断。

## 支持的文件

| 来源 | 格式 | 编码 | 表头位置 |
|---|---|---|---|
| 支付宝 | .csv / .zip（内含 csv）/ .xlsx | GBK | 前 4 行是账号与日期范围，表头在第 5 行左右 |
| 微信 | .csv / .xlsx | UTF-8 + BOM | 前 5 行是昵称与导出时间，表头行含「交易时间」 |

两条硬约束：

1. **表头按列名匹配，不按列序号**。两家的列数在版本间变过（支付宝从 16 列加到 17 列），按序号必然在某个版本上整体错位，错位的结果是「金额读成备注」这类静默错误。
2. **表头行按内容探测**：扫描前 20 行，找同时含「金额」列与「交易时间 / 交易创建时间」列的那一行。元信息行数与文案会变，不能写死行号。

列名归一（同一字段两家的写法）：交易号/交易单号 → `orderId`；交易对方 → `counterparty`；商品名称/商品 → `product`；支付方式/付款方式 → `payMethod`；收/支 → `direction`。

## 身份键（什么算「已存在」）

| 优先级 | 键 | 何时用 |
|---|---|---|
| 1 | 渠道 + 交易单号 | 有单号时（绝大多数） |
| 2 | 渠道 + 方向 + 金额 + 交易时间（到分） | 老版本导出没有单号 |
| 3 | — | 两条都不成立：跳过并计入失败明细，不猜 |

**跨源去重**：自动记账写的是 `auto_alipay`，导入写的是 `alipay_import`——同一笔会有两个来源。所以入库前**先按上表键查全库**（不限 source），命中就更新那一条，导入因此不会和自动记账重复记账。

**交易时间必须解析得出**：有单号时身份键成立，但时间列若写成「2026年11月」这类缺日/缺时刻的形态，这一行**计入失败并带行号**，不按「导入当天」兜底。原因：`date` 一旦落空串，月度统计、预算、可用月份全按 `date >= 'yyyy-MM-01'` 的字符串区间比较，这笔账会出现在最近列表里却永远不进任何月份——隐形账目比丢一行更难发现。

两种查重条件各有索引（`idx_finance_tx_source_id`、`idx_finance_tx_order_id`，数据库 V4 起）：没有它们时每行导入都是两次全表扫描，上千条 × 上万行会把单事务拖到几十秒。

## 更新语义（只补空，不覆盖）

命中已有记录时：只填**当前为空**的字段（商户 / 商品说明 / 付款方式 / 订单号 / 平台分类），不覆盖金额、分类、说明、日期。

- 为什么：用户改过一次分类，下次导入又改回去，等于每次导入都撤销他的编辑；补空不会。代价是「导入里更准的值」进不来——可接受，因为账本以用户为准。
- 例外：`orderId` 与 `sourceId` 一定写入（它们是身份不是用户内容）。

## 余额联动

导入的每一笔都走 `FinanceManager.insertTransactionWithEffect`：**交易写库与账户余额变更在同一个事务里**，账户按渠道固定（支付宝 → 支付宝，微信 → 微信钱包）。

- 为什么不能直接 `dao.insertTransaction`：那条路径不执行余额副作用，导入的账会永久不进账户余额，账目总额与余额从此对不上（历史缺陷）。
- 整批仍是**一个外层事务**（导入中途失败全部回滚，余额一并回滚）。
- 命中已有记录只补空时**不动余额**：金额 / 账户 / 日期都没变，再减一次就是重复扣。

## 分类推断（顺序即优先级）

1. **平台分类列**（仅部分导出版本有）；
2. **商品名称**：信息量最大（`某某湘菜馆外卖订单` 比商户名 `淘宝闪购` 准）；
3. **交易对方**；
4. 兜底：支出 → `其他`，收入 → `其他收入`。

关键词表集中在 `BillCategoryKeywords`，按一级分组，覆盖日常高频；与自动记账共用同一套映射结果（都落在 209 个分类内，二级优先）。

**不计入账本的行**（计入「跳过」而非「失败」，并在结果卡单列）：`交易关闭` / `已全额退款` / `不计收支` 的收/支值 / 转账到本人账户（提现、充值）。

## 文件与接口

| 文件 | 职责 |
|---|---|
| `finance/importer/BillRecord.kt` | 统一中间模型 + `BillChannel` |
| `finance/importer/BillFileParser.kt` | 入口：按文件名 + 内容识别渠道，产出 `List<BillRecord>` |
| `finance/importer/BillCsv.kt` / `BillXlsx.kt` / `BillZip.kt` | 三种容器解析（零第三方：系统 zip + XmlPullParser） |
| `finance/importer/BillColumns.kt` | 表头探测与列名归一 |
| `finance/importer/BillCategoryKeywords.kt` | 关键词 → 分类（纯数据） |
| `finance/importer/BillProductJson.kt` | 商品说明内嵌的平台分类（`{"支付宝交易分类":"…"}` / `支付宝交易分类=…`） |
| `finance/importer/BillImporter.kt` | 查重 / 补空 / 插入（走 FinanceManager 写入口，余额同步），整批单事务，产出 `BillImportResult` |

UI 复用 s08 导入页：文件选择按扩展名分流到两个 importer（`.csv/.xlsx/.zip` → 账单，`.db` → 熊猫），结果卡多出一格「更新 N 条」（仅账单导入且命中过已有记录时渲染）。

## 测试

Robolectric（真库）：导入支出后账户余额 -100、跨源只补空时余额不动、交易时间识别不出（「2026年11月」）计入失败且不以 `date=''` 落库；纯 JVM：表头探测（支付宝 4 行元信息 / 微信 5 行元信息 / 列顺序颠倒）、GBK 与 BOM 解码、引号内逗号与换行、xlsx 共享字符串与内联字符串、金额带 `¥` 与千分位、收入/支出/不计收支判定、身份键三档、跨源命中（auto_alipay 已存在时导入只更新不新增）、分类关键词命中与兜底，以及商品说明 JSON 与等号两种写法（正文里提到"分类"字样不误取）。
