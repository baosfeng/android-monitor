# 微信支付页识别调研（无障碍封锁与可行通道）

> ⚠️ **何时阅读：** 要让自动记账覆盖「微信支付完成后立即弹窗」、或排查「微信页面读不到节点 / 一直提示未收集到页面文本」时必读。
> 关联文档：→ [自动记账](自动记账.md) · [业界调研与实现方案](自动记账调研.md) · [踩坑：第三方悬浮窗顶掉无障碍根窗口](../踩坑/第三方悬浮窗顶掉无障碍根窗口.md)
> 状态：真机实测 + 多方一手资料交叉验证（2026-10-16）

## 结论速览

**微信会按「无障碍服务身份」定向隐藏页面节点树**：对不在它白名单里的第三方服务，把支付页 / 聊天页 / WebView 详情页的节点树隐藏掉；换成 Google 官方的 TalkBack，**同一个页面能读到完整 62KB 节点树**。

所以「微信支付后立即弹窗」在我们的测试机上读不到，**不是我们的解析规则问题，而是我们拿不到数据**。

## 一、真机实测（小米 14 / HyperOS / 微信 8.0.x）

### 1.1 微信各页面的无障碍可读性

| 微信页面 | 承载窗口 | 我们能读到吗 | 现在会弹窗吗 |
|---------|---------|------------|------------|
| 会话列表（微信首页） | `LauncherUI` | ✅ 22~25 行 | 不弹（门禁拒绝，符合预期） |
| 「微信支付」服务号会话页 | `LauncherUI` | ✅ 23 行（含消息卡片） | 不弹（用户要求只认详情页） |
| 服务号交易详情页（滴滴那笔） | `LauncherUI` | ✅ 完整字段 | **弹**（¥43.00 已实测） |
| **支付成功页**（发红包/转账后） | `UIPageFragmentActivity` | ❌ **0 行** | 读不到 |
| **转账详情页** | `MMWebViewUI` | ❌ **0 行** | 读不到 |
| **单聊页**（红包/转账消息） | `LauncherUI` | ❌ **0 行** | 读不到 |
| 付款确认面板（收银台） | `UIPageFragmentActivity` | ❌ **0 行** | 读不到 |

> 注意第 1 行与第 6 行**同为 `LauncherUI` 窗口**，一个能读、一个读不到 —— 说明微信是按**页面**动态隐藏，不是按窗口。

### 1.2 三个铁证

**证据 A：支付成功页读 8 次全空。** 用户实付一笔 ¥0.01 红包，支付成功页（视觉内容：`支付成功` / `待李四确认收款` / `¥0.01` / `完成`）停留约 12 秒，期间服务日志：

```
08:48:34.477 D AutoBook: 未收集到页面文本，跳过: com.tencent.mm
08:48:35.297 D AutoBook: 未收集到页面文本，跳过: com.tencent.mm
...（连续 8 次，覆盖整个支付成功页停留时间）
```

同期用连续截图（每秒 1 帧）拍下全过程，确认页面**视觉上完全正常**、且**没有 `FLAG_SECURE`**（否则截图会是黑屏）。

**证据 B：`uiautomator` 也读不到。** 支付成功页、转账详情页、单聊页，`adb shell uiautomator dump` 均只返回：

```xml
<hierarchy>
  <node bounds="[0,0][0,0]" package="com.tencent.mm" />
</hierarchy>
```

`uiautomator` 用的是系统级 UiAutomation，读数权限比普通无障碍服务更高 —— 它也读不到，说明不是我们的代码问题。

**证据 C：微信同时挂多个窗口，且我们已改为取「内容最丰富」的那个。** 真机窗口快照（每秒 1 次，共 76 次）：

```
t1  08:50:03  微信窗口: [LauncherUI]
t35 08:50:47  微信窗口: [MallIndexUIv2, LauncherUI]
t36 08:50:48  微信窗口: [UIPageFragmentActivity, MallIndexUIv2, LauncherUI]
t37 08:50:50  微信窗口: [UIPageFragmentActivity, MallIndexUIv2, MMWebViewUI, LauncherUI]
```

改造前我们只取「第一个包名匹配的窗口」，很可能取到栈底那个读不出内容的 `LauncherUI` 空壳。现已改为**逐个候选窗口试读、取内容最丰富的那个**（`AutoBookEngine.collectPageLines()`）。

### 1.3 已排除的可能

| 假设 | 结论 |
|------|------|
| 我们取错了窗口 | 已排除（改成取最丰富窗口后依然 0 行） |
| 无障碍配置不全 | 已排除，`flagReportViewIds\|flagRetrieveInteractiveWindows\|flagIncludeNotImportantViews\|flagRequestEnhancedWebAccessibility` 全开、`canRetrieveWindowContent=true` |
| `flagRequestEnhancedWebAccessibility` 能救 WebView | ❌ 实测无效（微信的 WebView 没有开 JS 无障碍注入） |
| 微信页面有 `FLAG_SECURE` 导致截屏失败 | 已排除（连续截图成功拍到支付成功页全貌） |
| 微信发系统通知可走通知通道 | ❌ 实测支付期间通知栏**没有**任何 `com.tencent.mm` 通知 |

## 二、根因：微信的无障碍服务白名单

AutoJs6 作者 SuperMonster003 在 [issue #463](https://github.com/SuperMonster003/AutoJs6/issues/463) 给出的权威解释：

> 因为微信有一套自己的无障碍服务白名单，但**仅仅是无障碍服务 ID 完整名称的后半部分**，前半部分的包名没有做验证。因此网上出现了不少把自身应用的无障碍服务名称（完整 ID 的后半部分）设置为白名单内的（典型的是 `com.google.android.accessibility.selecttospeak.SelectToSpeakService`），于是可以识别微信控件。

### 2.1 决定性交叉验证：TalkBack 能读

[mobilerun-portal issue #142](https://github.com/droidrun/mobilerun-portal/issues/142)（vivo OriginOS / Android 13 / 微信 8.0.74）做了我们做不了的对照实验：

| 无障碍服务 | `uiautomator dump` 微信的结果 |
|-----------|---------------------------|
| Mobilerun Portal（第三方） | 空壳（`<node bounds="[0,0][0,0]" package="com.tencent.mm" />`） |
| **TalkBack**（Google 官方） | **完整 62KB XML**，聊天列表项、底部 tab、`content-desc` 全部可读 |

切换回第三方服务后，树重新变空。**同一台手机、同一个微信版本、同一个页面，只换服务身份**，结果完全不同 —— 这就把「微信按服务身份定向隐藏」钉死了。

### 2.2 隐藏是怎么实现的

[ApkClaw PR #8](https://github.com/apkclaw-team/ApkClaw/pull/8) 的描述：

> 微信 8.0.52 版本开始，主动检测正在运行的无障碍服务。对于第三方服务（即非系统自带的服务），微信故意将 UI 节点树中的元素标记为不可见（`AccessibilityNodeInfo.isVisibleToUser() = false`）。

两种可能的实现，决定了我们还有没有救：

| 机制 | 表现 | 我们能否绕开 |
|------|------|------------|
| `importantForAccessibility = NO_HIDE_DESCENDANTS` | 系统**裁剪**整棵子树，`childCount = 0` | ❌ 读不到就是读不到 |
| `isVisibleToUser = false` / `bounds` 归零 | 树还在，只是标记不可见 | ⚠️ **有可能** —— 需要验证 |

[AutoJs6 issue #289](https://github.com/SuperMonster003/AutoJs6/issues/289) 与 [#382](https://github.com/SuperMonster003/AutoJs6/issues/382) 都报告「微信 8.0.54~8.0.58 控件获取不正确 / 无法布局分析」，说明这是长期对抗而非个例。

## 三、业界怎么绕过

| 项目 / 产品 | 做法 | 出处 |
|------------|------|------|
| **熊猫记账** | 把无障碍服务类名设为 `com.google.android.accessibility.selecttospeak.SelectToSpeakService`（真机 `enabled_accessibility_services` 已确认） | 本机实测 |
| **ApkClaw** | **双服务**：注册一个**完全空白**的伪装服务（FQN 与系统 SelectToSpeak 一致、`onAccessibilityEvent` 为空、`android:priority="10000"`）骗过白名单检查，真正的自动化由另一个服务执行 | [PR #8](https://github.com/apkclaw-team/ApkClaw/pull/8) |
| **touxian** | 采集服务放在 `com.google.android.accessibility.selecttospeak` 包名下并注册为 `SelectToSpeakService`，同时 `android:isAccessibilityTool="true"`；该项目自己把它列为 **P1 合规问题** | [issue #5](https://github.com/sssssjw11/touxian/issues/5) |
| **Auto.js（TonyJiangWJ 分支）** | 同样改成 `SelectToSpeakService` 类名应对微信混淆 | [issue #20](https://github.com/TonyJiangWJ/Auto.js/issues/20) |
| **AutoJs6（主流分支）** | **明确拒绝**做这种适配：认为「微信未来很可能加强白名单校验（加上包名验证），这些方法都会失效」，且不愿让服务名与功能不符 | [issue #463](https://github.com/SuperMonster003/AutoJs6/issues/463) |

### 3.1 伪装手法的合规风险（一手记录）

[touxian issue #5](https://github.com/sssssjw11/touxian/issues/5) 自己列的「风险」段落：

> 这会造成服务身份、真实用途和用户看到的系统无障碍服务名称不一致，也可能触及平台对无障碍 API、欺骗性界面和绕过安全控制的审核边界。

ApkClaw 的双服务做法并不能消除这个风险 —— 它只是让**真正干活的服务的名字**保持干净，伪装服务本身仍然是「伪装成系统服务」。

## 四、可行方案对比

| 方案 | 能否覆盖「微信支付后立即弹窗」 | 成本 | 风险 |
|------|---------------------------|------|------|
| **A. 双服务伪装**（空白 SelectToSpeak 服务 + 真实服务） | ✅ 大概率可以（业界已验证） | 低（约 1 个类 + manifest 条目） | ⚠️ 违反平台意图；微信随时可能加包名校验；应用商店审核风险 |
| **B. 截图 + OCR**（无障碍 `takeScreenshot()`） | ✅ 可以（截屏实测可用、非 `FLAG_SECURE`） | 中高（需离线中文 OCR 引擎，与项目「零第三方依赖」原则冲突） | 低（正规 API），但有性能开销与功耗 |
| **C. 通知监听**（NotificationListenerService） | ⚠️ 部分（微信**在后台**时的支付推送） | 中（需用户授权通知使用权） | 低 |
| **D. 只在可读页面识别**（现状） | ❌ 支付瞬间覆盖不到；交易详情页可以 | 零 | 零 |
| ~~E. Xposed / root~~ | ✅ | 高 | ❌ 需要 root，本机未 root |

## 五、待真机验证的实验清单

手机不在手边时无法验证的三件事，按优先级排列：

| # | 实验 | 怎么做 | 判定 |
|---|------|--------|------|
| 1 | **微信的隐藏是「裁剪子树」还是「标记不可见」** | 临时让 `NodeTextCollector` 在收集结果为空时，再跑一遍**不做 `bounds` 检查**的宽松收集，把读到的文本打进日志 | 能读到文本 → 属于「标记不可见」，去掉过滤即可解决；仍为空 → 属于「裁剪子树」，只能走 A 或 B |
| 2 | **`android:isAccessibilityTool="true"` 是否有效** | 给现有服务加上这个属性（这是 Android 12+ 的**正规** API，不是伪装），加完重启服务再读微信支付页 | 微信可能用它判断「是否为无障碍工具」，可能不伪装也能放行 |
| 3 | **通知通道的实际覆盖率** | 微信切到后台后再支付一笔，看通知栏是否出现 `com.tencent.mm` 通知 | 有通知 → 方案 C 可用作补充 |

> 实验 1 的现场线索：`app/src/main/java/com/bsfeng/monitor/autobook/NodeTextCollector.kt` 第 46 行有 `if (rect.width() > 0 && rect.height() > 0)`，而 mobilerun 抓到的微信隐藏节点正是 `bounds="[0,0][0,0]"` —— 如果微信只是把 bounds 归零，**我们会亲手把这些节点丢掉**。
