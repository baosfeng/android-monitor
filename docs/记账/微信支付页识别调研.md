# 微信支付页识别调研（无障碍封锁与破解）

> ⚠️ **何时阅读：** 要让自动记账覆盖微信支付、排查「微信页面读不到节点 / 一直提示未收集到页面文本 / 微信不再记账」时必读。
> 关联文档：→ [自动记账](自动记账.md) · [业界调研与实现方案](自动记账调研.md)
> 状态：**已解决**（真机实测 2026-10-16，小米 14 / HyperOS / Android 16 / 微信 8.0.79）

## 结论速览

微信按「**无障碍服务身份**」隐藏页面节点树：对不在它白名单里的第三方服务，直接在节点**生成阶段**跳过整棵树（我们读到 `root.childCount == 0`）。而它的白名单**只比对服务 ID 的后半段类名、不校验包名**。

因此解决办法是**把注册身份换成白名单里的类名**：本项目新增了一个什么都不做的伪装壳 `SelectToSpeakService`，manifest 用它注册。真机验证：**微信从「一个节点都读不到」变成「连支付成功页都能识别出金额」**。

## 一、封锁机制

微信 8.0.52 起按无障碍服务身份隐藏节点。机制的第一手解释来自 AutoJs6 作者 SuperMonster003（[issue #463](https://github.com/SuperMonster003/AutoJs6/issues/463)）：

> 微信有一套自己的无障碍服务白名单，但**仅仅是无障碍服务 ID 完整名称的后半部分**，前半部分的包名没有做验证。因此网上出现了不少把自身应用的无障碍服务名称（完整 ID 的后半部分）设置为白名单内的（典型的是 `com.google.android.accessibility.selecttospeak.SelectToSpeakService`）。

在 framework 层，这种「整棵树都不给」只可能来自节点**生成阶段**被跳过（[ViewGroup.addChildrenForAccessibility](https://github.com/aosp-mirror/platform_frameworks_base/blob/master/core/java/android/view/ViewGroup.java#L2477) 对每个 child 判 importance，false 就递归下钻，最终无子可加）。这排除了「标记为不可见 / bounds 归零」那类**生成之后**的属性标记 —— 后者忽略坐标仍能读到文本，前者不能。

## 二、三步实测（本项目取证过程）

### 步骤 1：`android:isAccessibilityTool="true"` —— 无效（已证伪）

思路：既然微信按「服务身份」判定，那声明自己是无障碍工具会不会放行？

| 证据 | 内容 |
|------|------|
| 前提确认 | 服务重连日志 `无障碍服务身份: isAccessibilityTool=true` —— 系统确实读到了该属性，**不是假阴性** |
| 结果 | 加上属性后，微信「支付成功」页在 22 秒内被读 12 次**全部为空** |
| 结论 | 微信不读这个标志。该属性已从 `accessibility_service_config.xml` 移除（它还会把「本服务是残障用户无障碍工具」这一不实声明带进 APK） |

### 步骤 2：窗口诊断 —— 确认「树被裁剪」而不是「标记不可见」

只靠「候选=[]」分不清「窗口不在清单里」和「窗口在但树是空的」，因此 `AutoBookEngine.logWindowDiagnostics()` 在读不到时打印交互窗口清单：

```
20:22:44.712 D/AutoBook: 窗口诊断: 目标=com.tencent.mm, 交互窗口共 3 个 ->
  [type=3,pkg=com.miui.home,      childCount=0,文本=0;
   type=3,pkg=com.android.systemui,childCount=2,文本=9;   <- 同一采集器读 systemui 正常
   type=1,pkg=com.tencent.mm,     childCount=0,文本=0]    <- 微信窗口在，但子树是空的
```

三条结论：① 微信窗口**在**我们的交互窗口清单里（不是窗口枚举问题）；② `childCount=0` 说明树在生成阶段就被跳过；③ 同一时刻读 systemui 有 9 条文本，**证明采集器本身正常**。

### 步骤 3：伪装白名单身份 —— 有效（最终方案）

把注册身份换成 `com.google.android.accessibility.selecttospeak.SelectToSpeakService` 后的真机日志（同一台手机、同一个微信）：

```
20:39:21.470  未识别到账单: com.tencent.mm [非账单页,门禁拒绝] 行数=12   <- 单聊页
20:39:25.117  未识别到账单: com.tencent.mm [非账单页,门禁拒绝] 行数=9    <- 转账输入页
20:39:41.342  未识别到账单: com.tencent.mm [门禁通过,字段不足] 行数=5
              文本=[使用密码 | 返回 | 请验证指纹 | 付款方式,已选择零钱,更改 更改 | 支付]   <- 收银台
20:39:42.943  识别到账单 channel=wechat type=支出 amount=0.01
              merchant=待李四确认收款 category=其他 account=微信钱包 markers=[支付成功]  <- 支付成功页
```

对照伪装前（2026-10-16 下午、同一台手机）：`未取到 com.tencent.mm 的有内容窗口，候选=[]`。

## 三、各页面可读性矩阵（伪装前后对照）

| 微信页面 | 承载窗口 | 伪装前 | 伪装后 |
|---------|---------|--------|--------|
| 会话列表 | `LauncherUI` | ❌ 0 行 | ✅ 可读 |
| 单聊页（红包 / 转账消息） | `LauncherUI` | ❌ 0 行 | ✅ 12 行 |
| 转账输入页 / 确认页 | `LauncherUI` | ❌ 0 行 | ✅ 9~10 行 |
| 收银台 / 指纹验证页 | `UIPageFragmentActivity` | ❌ 0 行 | ✅ 5 行（门禁通过） |
| **支付成功页** | `UIPageFragmentActivity` | ❌ 0 行 | ✅ **识别出金额与「支付成功」锚点** |
| 服务号交易详情页 | `LauncherUI` | ✅ 完整字段 | ✅ 完整字段 |

> 注意：伪装前连**会话列表**都读不到（`childCount=0`），这与当天更早一次实测「会话列表 22~25 行」不一致，该矛盾未解释 —— 可能微信的封锁状态是动态的。**伪装后不再有这个问题**。

## 四、本项目实现

| 改动 | 文件 | 说明 |
|------|------|------|
| 伪装壳服务类 | [SelectToSpeakService.kt](../../app/src/main/java/com/google/android/accessibility/selecttospeak/SelectToSpeakService.kt) | **不重写任何回调**，只是注册身份 |
| 业务类开放继承 | [MonitorAccessibilityService.kt](../../app/src/main/java/com/bsfeng/monitor/service/MonitorAccessibilityService.kt) | 只加了 `open`，业务代码一行未动 |
| manifest 注册身份 | [AndroidManifest.xml](../../app/src/main/AndroidManifest.xml) | 注册伪装壳，不是业务类 |
| 状态判定常量 | [AccessibilityStatus.kt](../../app/src/main/java/com/bsfeng/monitor/util/AccessibilityStatus.kt) | `SERVICE_CLASS` 跟随伪装名，否则设置页会误报「未开启」 |

> ⚠️ **换注册身份会让用户已开启的旧无障碍服务失效**，升级后必须在系统设置里重新开启一次「行为记录」。
> ⚠️ 这个服务同时是监控、开屏跳过、自动记账的生命线，关掉它等于全部停摆。

## 五、业界对照：为什么我们比 AutoAccounting 走得更远

| 项目 | 服务类名 | 支付页怎么读 |
|------|---------|-------------|
| **本项目** | `...selecttospeak.SelectToSpeakService`（伪装） | **无障碍直接读到**（真机实测） |
| [AutoAccounting](https://github.com/AutoAccountingOrg/AutoAccounting)（951★） | 同一个伪装名 | **OCR**（`canTakeScreenshot="true"` + ML Kit），无障碍节点只用于跟踪前台 Activity |
| [GKD](https://github.com/gkd-kit/gkd)（42927★） | 同一个伪装名（实现只有 4 行空壳子类） | 作者称支付完成页「微信给当前页面加了安全标记，无法显示属于正常行为」（[#909](https://github.com/gkd-kit/gkd/issues/909)） |
| [AutoJs6](https://github.com/SuperMonster003/AutoJs6)（6485★） | 明示拒绝伪装 | — |
| [ApkClaw](https://github.com/apkclaw-team/ApkClaw)（798★） | 空白诱饵服务 + 真实服务 | 双服务方案 |

穷举 GitHub 同类项目后：**没有任何项目在「不伪装 + 无 root」下读到微信支付页**；能覆盖支付页的方案全部改走 OCR / 通知 / Xposed。而我们实测**伪装后无障碍即可读到支付成功页** —— 说明本机（微信 8.0.79 / HyperOS）的安全标记没有拦到节点层。若哪天失效，OCR 是该领域的行业共识兜底（见第七节）。

## 六、风险与回退

**风险（改这里之前必读）：**

- **消耗品**：微信一旦加上包名校验，这条通路立即失效。AutoJs6 作者正是因此拒绝做同类适配；
- **违反平台意图**：服务名与真实用途不符 —— **仅供侧载自用，不要用它上架**（Google Play 对无障碍 API 有专门条款）；
- 微信对无障碍自动化有账号风控案例（强制下线 / 人脸验证），因此本项目**保持只读、不点击、不模拟操作**。

**回退**：把 [AndroidManifest.xml](../../app/src/main/AndroidManifest.xml) 里 service 的 `android:name` 改回 `.service.MonitorAccessibilityService`，并把 [AccessibilityStatus.kt](../../app/src/main/java/com/bsfeng/monitor/util/AccessibilityStatus.kt) 的 `SERVICE_CLASS` 同步改回。

## 七、备用通道（伪装失效时用）

| 通道 | 覆盖度 | 代价 | 依据 |
|------|--------|------|------|
| **截图 + OCR** | 能覆盖付款当场（本机支付页可截图，无 `FLAG_SECURE`） | 需引入离线中文 OCR（与「零第三方业务依赖」原则冲突）、约 1s 延迟 | 成熟方案的标准答案；`takeScreenshot()` 只需 `canTakeScreenshot="true"`（[AOSP](https://github.com/aosp-mirror/platform_frameworks_base/blob/master/services/accessibility/java/com/android/server/accessibility/AbstractAccessibilityServiceConnection.java#L1467)，333ms 节流） |
| 通知监听 NLS | 只覆盖「付款后离开微信」 | 需授权通知使用权 | 微信在前台付款不产生系统通知 |
| Shizuku + UiAutomation | 不稳定 | 需用户授权 Shizuku | GKD 的「自动化模式」即此路，真机反馈「随机失效」 |
| 官方账单导入 | 事后对账 | 手动导出 | 不受任何封锁影响 |
