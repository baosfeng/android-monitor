## 模块职责

在微信 / 支付宝的**单笔账单页**上识别出一笔账，弹出确认浮窗，用户确认后写入记账账本。

两条硬约束：

1. **不做静默自动记账** —— 识别结果一律要用户点一次「记一笔」。原因见 [调研文档 §6.1](自动记账调研.md)：无障碍识别存在不确定性（金额可能取错、商户可能为空），静默落库会污染账本，而浮窗一次点击的成本远低于事后排查。
2. **只认账单页** —— 首页、消息列表、账单流水一律不识别。真机反馈的「识别有误」就是首页消息摘要被当成了新交易，详见下面的「账单页门禁」。
   > 付款前页面（转账输入 / 收银台 / 指纹 / 确认付款）**不弹窗**，只做**预采集**（收款方 / 付款方式 / 用户备注），等支付成功页到了再合并 —— 见「付款前预采集」。

## 数据流

```
AccessibilityEvent（TYPE_WINDOW_STATE_CHANGED / CONTENT_CHANGED）
   ↓ 包名命中 AutoBookRules
   ↓ resolveTargetRoot()  按包名从 windows 里取窗口（不能用 rootInActiveWindow）
NodeTextCollector.collect()      节点 → (文本, 坐标)
   ↓
PageLines.toLines()              按 Y 分行、行内按 X 排序 → 「标签 值」视觉行
   ↓
AutoBookParser.parse()           支付成功页 → AutoBookDraft（门禁 + 字段 + 去重键）
   │ 解析失败
   └→ AutoBookParser.parsePrePayment()  付款前页面 → 只缓存 PrePaymentDraft（收款方 / 备注），不弹窗
   ↓
AutoBookDraftMerger.merge()      成功页空白的字段用预采集补齐（成功页优先）
   ↓
AutoBookDedup.blockedReason()    短期去重：同一笔在安静期内直接返回，不弹窗
   ↓
AutoBookEngine.showOverlay()     检测到支付成功页就立即展示（不再延迟）
   ↓
AutoBookOverlay.show()           全屏遮罩 + 实心确认卡 → WindowManager + ComposeView，跟随 App 主题
   ↓ 用户点「记一笔」/ 点「忽略」/ 点遮罩
AutoBookEngine.persist()         幂等落库（source + sourceId 去重）→ finance.db
```

## 确认浮窗显示契约（v2，2026-10-17 真机反馈后重做）

真机反馈：① 面板在玻璃拟态主题下半透明，透出支付页文字；② 浮层没盖住状态栏（不沉浸）。

出现时机：**检测到支付成功页就立即展示**（2026-10-17 用户要求去掉 1s 延迟）。付款前页面
（收银台 / 指纹 / 转账输入 / 备注弹窗）由 `PRE_PAY_WORDS` 拒绝，只做预采集，不会提前弹。

| 项 | 规格 | 实现位置 |
|----|------|---------|
| **出现时机** | 识别到支付成功页后 **立即展示**；不再延迟、不做到点复核 | `AutoBookEngine.showOverlay()` |
| **全屏遮罩** | 窗口铺满整屏（`fitInsetsTypes = 0` + 挖孔区 `ALWAYS` + `FLAG_LAYOUT_IN_SCREEN`）；遮罩叠两层 ≈ **0.56**，覆盖状态栏 / 挖孔区 / 手势条；点遮罩 = 忽略 | `AutoBookOverlay.show()` |
| **面板实心** | `opaquePanel` = surface-warm → surface → bg 合成到 **100% 不透明**（玻璃主题下为 `#f2f8ff`），不再透出支付页 | `AutoBookConfirmSheet` / `DesignTokenCatalog.opaquePanel` |
| **状态栏图标** | 遮罩是深色，目标切浅色（`isAppearanceLightStatusBars = false`）；图标最终由 systemui 决定，ROM 可能有差异 | `AutoBookOverlay.show()` |
| **动效** | 遮罩淡入 180ms + 卡片从底部滑入 220ms；关闭即时卸载（保持既有行为） | `AutoBookOverlay` |
| **分类区域** | **4 列图标网格**（与「记一笔」同一套分类格）：一屏 3 行（默认 12 个分类全可见），分类更多时可上下滑；选中项自动滚入可视区 | `AutoBookConfirmSheet.CategoryGrid` |
| **备注行** | 付款前页面预采集到用户备注时，浮窗多一行「备注 午饭」；没有则整行不显示 | `AutoBookConfirmSheet` / `AutoBookDraft.userRemark` |

> ⚠️ **遮罩是有意加深的**：原型 `scrim` 是 0.34，浮层盖在**别的 App** 上时太浅会让人分不清哪一层可点；叠两层 ≈ 0.56 与窗口级浮层（`WindowOverlay`）同一口径。
>
> ⚠️ **面板实心是对玻璃拟态主题的有意偏离**：确认卡里是要读、要点的字段，不能透出下层文字；
> 其余页面继续保留玻璃语言。

## 付款前预采集（收款方 / 备注只在付款页有）

真机反馈（2026-10-17）：「应该在我这个页面就已经准备记录内容了，然后等我支付成功之后再弹，因为这个还存在备注等相关的信息」。

微信转账 / 支付宝确认付款的**收款方、付款方式、用户填的备注**只出现在付款前页面；支付成功页往往是极简静态页
（微信转账成功页只有 `支付成功 + 金额 + 完成`）。所以：

| 阶段 | 行为 |
|------|------|
| 付款前页面（微信转账输入 / 收银台 / 指纹 / 确认付款；支付宝转账输入 / 添加备注弹窗） | **不弹窗**；`AutoBookParser.parsePrePayment()` 预采集 金额 / 收款方 / 付款方式 / 备注，按字段**累积**（输入页的备注不会被收银台页冲掉） |
| 支付成功页 | 正常解析；`AutoBookDraftMerger.merge()` 用预采集补成功页空白的字段（**成功页有的优先**） |
| 合并条件 | 同渠道 + 金额一致（±0.01）+ 预采集未过期（`PRE_DRAFT_TTL_MS = 120s`）；不满足就原样使用成功页结果 |
| 清理 | 浮窗真正展示后清空预采集；服务销毁时清空 |

纯逻辑实现：`AutoBookParser.parsePrePayment()` / `AutoBookDraftMerger`（`accumulate()` + `merge()`），单测见 `AutoBookPrePaymentTest`。

### 支付宝红包：付款成功后没有结果页，回聊天页

真机实测（2026-10-17 16:28 / 16:45）：

| 阶段 | 页面文本 | 行为 |
|------|---------|------|
| 发红包确认页 | `返回 | 发红包 | 0.01 | 示例留言 | 红包封面 | 24小时内未被领取…` | **不弹窗**；`isRedPacketPrePayPage()` 打「正在发红包」标记 + 预采集金额 |
| 收银台 / 指纹页 | `发普通红包` / `请验证指纹` | 标记保持；指纹页仍被 `PRE_PAY_WORDS` 拒绝 |
| 聊天页（发出后） | `返回 资金往来记录 聊天设置 | 张三 | ¥0.01 | 示例留言 | 支付宝红包 16:45 | …` | `parseSentRedPacketChat()` 识别为**支出**，金额取预采集（缺失时取气泡金额），商户取领取人 / 联系人 |

关键点：

- 支付宝红包**没有** `支付成功` 锚点页，发完直接回聊天页；聊天页里本来就有历史红包气泡。
- 因此**不能只凭「页面有红包」就弹**：必须满足「刚走过红包付款前页面」（`isRedPacketPrePayPage` → `redPacketPaymentPending`），
  且聊天页出现 `支付宝红包` 气泡，气泡金额与预采集一致（±0.01）。
- 对方已领取时页面有 `红包已被领取` / `领取了你的 红包` 强信号，此时金额以预采集为准；
  对方**没领取**时气泡只带 `支付宝红包 + ¥0.01 + 留言`，靠气泡金额兜底。
- 预采集因服务重启丢失时，只要还处于「刚发红包」状态，仍可用气泡金额补记（真机 16:45 走的正是这条）。

实现在 [`AutoBookParser.parseSentRedPacketChat()`](../../app/src/main/java/com/bsfeng/monitor/autobook/AutoBookParser.kt) + [`AutoBookEngine` 的红包聊天页兜底分支](../../app/src/main/java/com/bsfeng/monitor/autobook/AutoBookEngine.kt)；单测见 [AutoBookParserTest](../../app/src/test/java/com/bsfeng/monitor/autobook/AutoBookParserTest.kt)。

## 记住上次选的类型 / 分类（按商户）

需求（2026-10-17）：「如果我上次扫过一家店，选的类型是什么，现在默认帮我勾选，否则就和现在一样」。

| 规则 | 实现 |
|------|------|
| 匹配键 | **商户名精确匹配**（`FinanceDao.findLastByMerchant()`）；只查**已确认落库**的记录，忽略 / 只是弹过没记的不算 |
| 默认值 | 上次记录的 `type` + `categoryName` 作为浮窗初始勾选；商户为空 / 无历史 → 保持解析器结果（与现状一致） |
| 边界 | 历史类型非法 → 只沿用分类；历史分类为空 → 只沿用类型 |
| 查询时机 | 浮窗展示前（`AutoBookEngine.showOverlay()`）；查库失败按无历史处理，绝不影响弹窗 |

纯逻辑：`AutoBookDefaults`（5 例单测）+ `FinanceDaoTest` 1 例（Robolectric 真实 SQLite）。

## 账单页门禁（只认账单页）

> **背景**：用户在支付宝**首页**看到浮窗弹了出来 —— 首页「最近消息」卡片里有一条历史消息摘要 `付款成功￥3.00`，
> 与支付结果页文案一模一样，被认成了一笔 3 元支出，商户名还写成了「松开刷新」。
>
> 复现日志（改造前）：
> ```
> I AutoBook: 识别到账单 channel=alipay type=支出 amount=3.0 merchant=松开刷新 markers=[付款成功]
> I AutoBook: 识别到账单 channel=alipay type=支出 amount=3.0 merchant=上海 搜索框 搜索服务或小程序 搜索 更多操作
> ```
> 同一屏连弹两次（两次商户名不同 → 去重键也漂移），两个缺陷叠在一起。

判定顺序**就是设计本身**（`AutoBookParser.isBillPage()`）：

| 步骤 | 判定 | 真机依据 |
|------|------|---------|
| 0 | **付款前页面**（收银台 / 指纹 / 密码输入）→ 拒 | 微信转账指纹页同样带「付款方式 + 零钱 + 金额」，旧门禁会放行 → 用户还没付完就弹窗；`PRE_PAY_WORDS` 命中即拒 |
| 1 | **≥2 处付款方式标签 或 ≥2 个不同金额** → 拒 | 支付宝「支付消息」列表每张卡片都自带「付款方式」；**不能数「支付成功」出现次数** —— 支付宝结果页标题与正文各有一处，会误杀单笔结果页（真机 2026-10-17） |
| 2 | **有「标签 → 值」结构** → 放行 | 账单详情页：`创建时间` / `付款方式` / `收款方全称` / `账单分类` / `商品说明` |
| 3 | **列表 / 摘要页特征** → 拒 | 首页：`最近消息`、`还有3条未读服务消息`、`2小时前`、`松开刷新` |
| 4 | **整行状态锚点 + 收尾按钮** → 放行 | 付款后立即跳出的结果页：`支付成功` + `¥25.00` + `完成` |
| 5 | **微信红包结果页**（红包 + 金额 + 支付方式）→ 放行 | 微信红包付款成功后**没有**锚点页、聊天页红包气泡又不含金额 —— 不认这一页红包就永远记不上 |
| 6 | **支付宝红包聊天页** → 不走 `isBillPage`，由 `AutoBookEngine` 单独兜底 | 支付宝红包没有结果页，直接回聊天页；由「刚走过红包付款页」标记 + `支付宝红包` 气泡识别，详见上一节 |

对应的实现位置：

| 判定 | 方法 |
|------|------|
| 付款前页面 | `AutoBookParser.isBillPage()` 开头的 `PRE_PAY_WORDS`（`请验证指纹` / `使用密码` / `立即支付` / `确认付款` …） |
| 多笔痕迹 | `AutoBookParser.hasMultipleTransactions()`（付款方式标签数 / **不同金额**数，阈值 `MULTI_TRANSACTION_THRESHOLD = 2`） |
| 详情结构 | `AutoBookParser.hasDetailStructure()`（标签集 `DETAIL_LABELS`） |
| 列表 / 摘要页 | `AutoBookParser.isListOrSummaryPage()`（`LIST_PAGE_WORDS` + `RELATIVE_TIME`） |
| 独占结果页 | `AutoBookParser.isStandaloneResultPage()`（`STATUS_ANCHOR` + `RESULT_PAGE_ACTIONS`） |
| 红包结果页 | `AutoBookParser.isRedPacketResultPage()`（`RED_PACKET_PRE_PAY_WORDS` 负责把付款前的输入页/收银台/指纹页挡在外面） |

> ⚠️ **顺序不能调换**：`hasDetailStructure` 必须排在 `hasMultipleTransactions` **之后**。
> 支付消息列表页每张卡片都有「付款方式」，先判详情结构就会把它整页放行。

### 页面判定（规则层）

命中 [AutoBookRule.pageMarkers](file://~/android-monitor/app/src/main/java/com/bsfeng/monitor/autobook/AutoBookRule.kt) 里任意一个特征词才进入门禁：`交易成功` / `账单详情` / `支付成功` / `付款成功` / `转账成功` / `你有一笔` …

命中 `excludeMarkers`（`账单统计` / `收支分析` / `月账单` / `年度账单`）直接放弃。

> ⚠️ **排除词里不要加「全部账单」「账单管理」** —— 真机实测这两个词就出现在账单**详情页**上（右上角按钮 + 底部入口），加进去会导致详情页整页被排除。

## 字段提取

| 字段 | 取值方式 | 兜底 |
|------|---------|------|
| 金额 | 带方向前缀（`支出3元`）> 带 `¥` > 带 `元` > 裸两位小数（`-3.00`） | 取不到则不弹窗 |
| 方向 | 金额行自带方向词 > 收入词 > 支出词（**判定前先清洗品牌名与方向标签**：`收款方` / `付款方` / `待…确认收款` 只表达「谁收谁付」，不表达方向） | 默认支出 |
| 商户 | `收款方全称` / `商户全称` / `商户名称` … 标签的同行右侧内容 | 页面靠前的可用短文本；再取不到用付款前页面的收款方（`付款给…`）；都取不到留空 |
| 备注 | 付款前页面的「备注 / 转账说明」原文（微信输入页 / 支付宝确认页）；「修改 / 添加备注」是入口文案，不算 | 空则不展示 |
| 分类 | 平台自带分类（`日用百货` → 日用）优先 | 商户关键词；再兜底「其他」 |
| 账户 | 固定取 App 账户体系（支付宝 / 微信钱包），保证记账能算进余额 | 规则里配置 |
| 支付方式 | `付款方式` / `支付方式` / `交易方式` 标签值（余额宝 / 零钱）；**微信的「已选择零钱，更改」会归一成「零钱」**（去掉「已选择」前缀、「更改」入口与值前逗号） | 空则不展示 |
| 时间 | `支付时间` / `交易时间` / `创建时间` 标签值，或全页首个日期时间串 | 空则不展示 |
| 订单号 | `订单号` / `业务交易号` … 标签值（**含行内标签**，见下） | 取不到留空 |

> ⚠️ **标签取值有「前缀误命中」防护**（`AutoBookParser.labelValue()` + `isCjkIdeograph()`）：
> 短标签会命中长标签并取出半截值 —— 真机踩到「付款方」命中「付款方式」，商户名被写成 `式 招商银行信用卡(8888)`。
> 现在**标签后面紧跟汉字即视为更长词的片段并跳过**（紧跟冒号 / 空格 / 字母数字仍然放行）。
> 相应地，`MERCHANT_LABELS` 里**不放「付款方」**（它本来也不是商户，是转账的转出方）。

> ⚠️ **订单号常常不给单独一行**：真机支付宝把它塞在别的值里 ——
> `商品说明 充值:阿里云服务购买,业务交易号:CFP000000000000000000`。
> `extractOrderId()` 除了按标签取，还会再扫一遍行内标签（`ORDER_LABEL_INLINE`）。

## 同一笔只弹一次（去重）

真机上同一笔账单会被反复触发：账单页自己会连抛多个 `CONTENT_CHANGED`，用户来回切页也会重新触发。分三层挡住：

| 层 | 位置 | 作用 |
|----|------|------|
| 1. 事件节流 | `AutoBookEventThrottle`（**只节流 CONTENT_CHANGED**，800ms；WINDOW_STATE_CHANGED 永远放行） | 挡住连续内容变化；**页面切换不能被吃掉**（真机：支付成功页在指纹页后 402ms 到达，旧实现直接丢弃） |
| 2. 短期去重表 | `autobook/AutoBookDedup.kt` | 按指纹记住三种结局，各有安静期 |
| 3. 落库查库 | `AutoBookEngine.isAlreadyBooked()` | 覆盖进程重启：已记账的永久不再弹 |

### 三种结局与安静期

| 结局 | 何时写入 | 安静期 |
|------|---------|--------|
| `CONFIRMED` | 用户点「记一笔」（**先打标再落库**） | 10 分钟（`AutoBookDedup.CONFIRMED_TTL_MS`） |
| `DISMISSED` | 用户点「忽略」 | 10 分钟（`AutoBookDedup.DISMISSED_TTL_MS`） |
| `SHOWN` | 浮窗弹出（用户尚未操作） | 30 秒（精确指纹，`SHOWN_TTL_MS`）/ **5 秒**（金额模糊指纹，`FUZZY_SHOWN_TTL_MS`） |

### 指纹为什么是多条（关键）

一笔账会同时产出**多条**指纹（`AutoBookParser.buildDedupKeys()`），**任一命中即视为「这笔刚处理过」**：

| 指纹 | 形态 | 安静期 |
|------|------|--------|
| 订单号（精确） | `order:alipay:CFP000000000000000000` | 10 分钟 |
| 交易时间（精确） | `time:alipay:0:3.0:2026-10-15 23:14:43` | 10 分钟 |
| 金额兜底（**模糊**，`precise = false`） | `sum:alipay:0:3.0` | **只在「刚弹过」时做 5 秒防抖**，不参与「已忽略 / 已记账」（见下） |

三个刻意的设计决定：

1. **指纹里绝不掺「当前时间」**。改造前用「渠道+方向+金额+商户+5 分钟时间桶」，同一笔跨过桶边界就换了键，
   短期去重直接失效 —— 这是「同一笔反复弹窗」的根因之一。**交易时间是账单自带属性，跨时间稳定，可以参与指纹。**
2. **指纹里绝不掺商户名**。真机实测同一笔在支付宝首页两次识别出的商户名完全不同（一次「松开刷新」、
   一次「上海 搜索框 搜索服务或小程序 搜索 更多操作」），指纹只要带了商户名就会算出两个键、连弹两次。
   商户名只能进**落库键**。
3. **模糊指纹（金额兜底）不承担跨分钟记忆**。`sum:` 键里**没有任何信息能区分「同一笔」和「另一笔同金额」** ——
   真机实测（2026-10-16 微信）：用户忽略一笔 ¥0.01 转账后 11 秒发出 ¥0.01 红包，红包撞上同一个模糊键
   （`sum:wechat:0:0.01`）被**静默吞掉、浮窗不弹**。因此模糊键只在 `Outcome.SHOWN` 时写入；
   已记账那一侧由落库键（含 5 分钟时间桶）+ 查库兜底保证，不受影响。
   
   **再实测（2026-10-17 微信）**：16:15:40 弹过一笔 ¥0.01，16:16:02 另一笔 ¥0.01 撞上 `sum:wechat:0:0.01`
   剩余 8s 的 **30 秒**窗口被静默吞掉 —— 用户以为是「二维码识别入口」失效。现在模糊键的 SHOWN 防抖
   收紧到 **5 秒**（足够挡住同一页面的重复事件，不会盖住下一笔同金额交易）。

### 落库键（sourceId）与去重指纹是两套

| 用途 | 键 | 策略 |
|------|----|------|
| **弹窗去重** | `buildDedupKeys()` 多指纹 | 精确键长安静期 + 模糊键短安静期，任一命中即不弹 |
| **落库幂等** | `buildSourceId()` 单键 | 订单号 > 交易时间 > 「渠道+方向+金额+商户+5 分钟桶」 |

> ⚠️ **落库键最后一档故意保留时间桶**：落库这一侧宁可重复也不能丢账。
> 若拿「渠道+方向+金额」当唯一键，用户连着买两笔 3 元会被合并成一笔，那是真的丢账。
> 「同一笔反复弹窗」这个痛点由去重指纹单独解决，不靠这个键。

## 明确不记的情况

| 情况 | 原因 |
|------|------|
| 无金额 | 无法记账（「你有一笔交易，点此查看详情」这类） |
| 提现 / 充值（`提现到` / `充值成功` …） | 账户间转移，记了会让总身家凭空变化 |
| 未来时态（`将于` / `即将` / `待扣` / `续费提醒`） | 钱还没扣，不是已发生的交易 |
| 金额落在余额/额度/优惠/积分上下文 | 余额不是交易金额 |
| **不是账单页**（首页 / 消息列表 / 账单流水） | 见「账单页门禁」，真机反馈「识别有误」的主因 |

## 真机调试

统一日志 tag：**`AutoBook`**

```bash
# 1) 看识别链路
~/android-platform-tools/adb logcat -s AutoBook

# 2) 复现：切到桌面再切回目标 App（触发 WINDOW_STATE_CHANGED）
~/android-platform-tools/adb shell input keyevent KEYCODE_HOME
~/android-platform-tools/adb shell monkey -p com.eg.android.AlipayGphone -c android.intent.category.LAUNCHER 1
```

日志会明确区分六种情况（这是排查「为什么没弹窗」的关键）：

| 日志 | 含义 |
|------|------|
| `未取到 <包名> 的窗口，当前窗口=[...]` | 页面没开，或被第三方悬浮窗顶掉了（看方括号里的窗口清单） |
| `未收集到页面文本` | 窗口在但树是空的 |
| `未识别到账单: <包名> [非账单页,门禁拒绝] ...` | **门禁挡住了** —— 当前页不是账单页（首页 / 列表页），这是预期行为 |
| `未识别到账单: <包名> [门禁通过,字段不足] ...` | 是账单页但字段没认出来 —— **看方括号里的实际文本**，据此调正则或加标签 |
| `识别到账单 channel=... amount=...` | 识别成功，随后进入去重 |
| `去重命中，本次不弹窗：<原因>（key=... 剩余 Ns）` | **被短期去重挡住** —— 原因会说清是「已记账 / 已忽略 / 刚弹过」 |
| `该笔已记账（查库命中），不再弹窗` | 数据库里已有这笔（跨进程重启后的持久化去重） |

> ⚠️ **截图取证的顺序：先截图，再 `uiautomator dump`。**
> `uiautomator dump` 会断开设备上其它无障碍服务，导致我们的服务被销毁、浮窗被 `release()` 收掉，
> 出现「日志说弹了、截图看不到」的假象。详见 [踩坑：uiautomator 会踢掉无障碍服务](../踩坑/uiautomator踢掉无障碍服务.md)。

## 后续计划（调研已给出做法，尚未实施）

| 项 | 做法（有源码依据） | 价值 |
|----|------------------|------|
| 通知通道（NotificationListenerService） | 走 `AutoBookParser.parseNotification()`（**不做页面门禁**，通知来源明确）；文本按 `TITLE → TEXT → BIG_TEXT → TEXT_LINES → SUB_TEXT → SUMMARY_TEXT → ticker` 合并并按包含关系去重 | 覆盖微信无障碍拿不到的场景，成本最低 |
| 事件收敛升级 | `TYPE_WINDOW_STATE_CHANGED` 只更新前台包名/Activity，`CONTENT_CHANGED` 走「500ms 防抖 + 结构指纹门禁」再进识别（当前是 800ms 节流 + 多指纹去重） | 长列表/高频页面下减少无谓解析 |
| 字段提取改为「锚点 + 邻域」 | 支付宝用 `^(支付成功|转账成功)[¥￥]\d+\.\d{2}$` 锚点 + 尾部按钮裁剪 + 剩余两两成对还原键值对 | 比当前的标签取值更抗「新增一行就错位」 |
| 分类映射补行业词 | 真机「某市供水公司」落到了「其他」，可给 `MERCHANT_CATEGORY_KEYWORDS` 的水电组补 `水务` / `自来水` | 减少用户手动改分类 |
| 小程序 / WebView 页 | 无障碍对 WebView 子节点支持有限（子控件无 id、`findAccessibilityNodeInfosByText` 对 WebView 无效），需 `flagRequestEnhancedWebAccessibility` + 遍历 WebView 子节点，或退到截图 + OCR | 覆盖支付宝小程序类支付页 |
| 账单导入通道 | 微信跳 17 行 / 支付宝跳 22 行 + GB18030 解码，改用「表头别名 + 第一条可解析时间行」定位；退款单号是原单号前缀需特判 | 不依赖任何运行时权限的对账兜底，也是上架合规的「更窄替代方案」 |

> ⚠️ **第三方全屏悬浮窗会顶掉根窗口**：真机实测时「熊猫记账」的记账确认窗一直盖在支付宝页面上，此时 `windows` 里只剩它一个窗口，支付页完全读不到。已按包名取窗口规避（见 [踩坑记录](../踩坑/第三方悬浮窗顶掉无障碍根窗口.md)）。
>
> ⚠️ **微信会同时挂多个窗口**（真机实测 `LauncherUI` / `MallIndexUIv2` / `UIPageFragmentActivity` / `MMWebViewUI`），栈底那个 `LauncherUI` 常常是读不出内容的空壳。已改为**逐个候选窗口试读、取内容最丰富的那个**（`AutoBookEngine.collectPageLines()`）。
>
> ✅ **微信的支付页 / 聊天页已可读（2026-10-16 解决）**：微信按「无障碍服务身份」隐藏节点树，本项目把注册身份换成它白名单里的类名（`com.google.android.accessibility.selecttospeak.SelectToSpeakService`）后即放行，连支付成功页都能识别出金额。机制、三步实测证据、风险与回退见 [微信支付页识别调研](微信支付页识别调研.md)。
