# 定位能力基线（对标成熟产品）

> 何时读：改动定位采集 / 掉线自愈 / 轨迹后处理 / 轨迹图前。本文是**差距清单 + 已落地口径**，不是实现说明。结论：取点、省电、精度表达三块已可用；欠的是「位置数据保留期」这类产品能力，不是算法。

## 两条硬约束（决定排期顺序，不是偏好）

| 约束 | 出处 | 对我们的影响 |
|---|---|---|
| 未获 `ACCESS_BACKGROUND_LOCATION` 时，**不能在后台创建 location 类型前台服务**（抛 SecurityException） | [FGS 类型](https://developer.android.google.cn/develop/background-work/services/fgs/service-types?hl=zh-cn) | 前台服务救不了「缺后台定位」的用户 → **必须先修权限四态，再上前台服务** |
| Doze 下 `setAndAllowWhileIdle` **每 9 分钟最多一次**；App Standby rare bucket 还会再降频 | [Doze 文档](https://developer.android.google.cn/training/monitoring-device-state/doze-standby?hl=zh-cn) | 现在靠 `setInexactRepeating` 1 分钟心跳兜底，深睡时必然断；只提闹钟精度治不好 |

另两条易踩：targetSdk≥34 未声明 `foregroundServiceType` 时 `startForeground` 直接抛异常；Android 12+ **只申请 FINE 会被系统忽略**，必须 FINE + COARSE 同批。

## 差距盘点

### P0 · 用户可感知的故障

| 问题 | 现状 | 对标做法 |
|---|---|---|
| 只给「大致位置」被当成「已就绪」 | `isFineGranted()` 用 FINE \|\| COARSE；三态枚举无 COARSE_ONLY | 大致位置单独一态并明示「轨迹不可靠」 |
| ~~后台存活依赖 inexact 闹钟~~ | **已修**：`LocationForegroundService`（location 类型 + `START_STICKY`）承载采集，ticker 与订阅从无障碍服务迁出；1 分钟心跳仍兜底 | 同上 |
| ~~掉线不可观测~~ | **已修**：`CoverageTimeline` 分段 + 设置页「采集覆盖」卡（过去 24 小时覆盖条 + 断档列表），口径见下节「待机 ≠ 断档」 | Traccar / OwnTracks 有连接状态时间线 |

### P1 · 市面标配，未做

| 能力 | 对标 | 现状 |
|---|---|---|
| ~~轨迹不表达不确定~~ | 高德蓝点精度圈；`Location.getAccuracy()` 是 **68% 置信半径**不是上界 | **已修**：低置信段画虚线 + 粗坐标日提示，见下节「精度表达」 |
| 逐点误差圈 | 高德 / Strava 在当前点画 68% 半径圈 | **未做**：线型只表达「哪一段不可全信」，不表达「偏了多少米」；要画圈得按 accuracy 外扩并处理重叠 |
| 地图交互 | 拖动 / 缩放 / 跟随视角 | Canvas 静态渲染 |

### P2 · 做了但不够好

- **采样字段丢太多**：只留 provider/lat/lng/accuracy/time，`speed`/`bearing`/`speedAccuracy`/`elapsedRealtimeNanos`/`isMock` 全丢 → 算不出配速、画不了方向、「速度精度」这道质量闸用不上。
- **历史坐标仍是 110m**：库里 855/1056 条是 3 位小数，修复只对新数据生效、老轨迹无迁移 —— 靠轨迹卡「粗坐标日」提示兜住认知，**不靠算法补精度**（见下节）。
- **注释与常量不符**：`NETWORK_LOW_LIMIT_METERS = 500f`，但同文件与 `LocationRules` 注释写「≤2000m」。

## 精度表达（`ui/trip/TracePrecision.kt`，已落地）

| 项 | 口径 |
|---|---|
| 分档 | `accuracy ≤ LocationQuality.HIGH_ACCURACY_METERS`（100m）为高置信；> 100m 低置信；**缺精度按高置信**（不虚构不确定） |
| 画法 | 相邻两点任一端低置信 → 该段**虚线**；两端都高置信 → 实线。线宽 1.5dp、颜色 accent 不变，**只换 dash** |
| 为什么用线型 | 灰度屏 / 色弱分不清颜色深浅，形状差异才可读；导出 PNG 与屏内同一套判定 |
| 图例第二行 | 「虚线 = 精度 > 100m（可能偏几百米）」**只在当天存在低置信段时**渲染，没有就整行不渲染 |
| 粗坐标日判定 | 某天 ≥60% 采样落在 3 位小数网格（0.001° ≈110m）→ 历史粗坐标日 |
| 粗坐标日表现 | 卡内一行提示「坐标只存 3 位小数（≈110m），这天不做平滑：阶梯是量化造成的」 |

## 轨迹平滑（`ui/trip/TripDenoise.kt`，已落地）

四条不变量 + 两档窗口；粗坐标日整条跳过平滑。

| 项 | 口径 |
|---|---|
| 管线 | parse → rejectOutliers → smooth → dedupe → simplify → cap（`TripTrace.samples`） |
| 权重 | ∝ 1/accuracy²；缺精度按 50m |
| 两档窗口 | 局部静止（相邻位移 ≤ max(两端精度和, 15m)）→ ±3 分钟且 ±14 点；在动 → ±60 秒且 ±2 点 |
| 分段 | 跨 >5 分钟断档分段，不跨断档平滑 |
| 拐点保护 | 偏离弦 > max(10m, 2×段内精度中位数) 保留原坐标 |
| 首尾 | 每段首尾不参与平均 |
| **粗坐标日** | **跳过平滑**：110m 网格被平均会变成斜线 = 伪造精度；阶梯本身就是「只准到 110m」的证据 |
| 实测 | 静止抖动（60 点 / ±30m / accuracy 30m）平均偏差 **22.7m → 4.58m（-79.8%）**；整天静止剩余点 **43 → 4**；步行段坐标变化 **0.0m**；直角拐点位移 **0.0m** |

## 耗电与探测（`record/LocationRules.kt` + `record/LocationTickerPolicy.kt`，已落地）

| 项 | 口径 |
|---|---|
| 探测预算分级 | 门禁探测 / SLEEPING 兜底：network **4s** + gps **8s**，单次射频上限 **12s**（原满预算 20s）；命中 ≤90s 系统缓存时 **0s** |
| 满预算路径 | MOVING 静默补采 / 断档自愈 / 首点兜底**不变**：network 5s + gps 15s（20s）。断档自愈会升级到满预算，**唯一例外是门禁 SLEEPING**：它的 30 分钟兜底距上次成功必然 ≥30 分钟、每次都被判成断档，升级等于把「常态静默」全变成 20 秒射频 |
| 心跳取档 | 心跳按门禁态取同一档 —— 否则 12s 上限会被心跳后门打破 |
| 90s 缓存窗口 | force 探测允许 ≤90s 缓存点顶替主动定位（须过 `LocationQuality` 质量闸），该点同样进门禁位移证据链。探测周期本身 180s 起，90s 内的点与刚探测的点在位移判定上等价；更旧的算不出「现在在哪」 |
| 退避阶梯 | 连续无位移证据的探测：0~2 次 **180s** / 3~5 次 **300s** / ≥6 次 **600s**；任何运动证据（步数 / 步态 / 抖动 / 位移过噪声地板）立刻回 180s。手持静坐 1 小时探测次数 **20 → 9** |
| ticker 拍子 | SLEEPING `min(5 分钟, 距兜底剩余)`、下限 30s；MOVING / PROBING 仍 30s；状态迁移同一拍重排 |
| 兜底不变量 | SLEEPING 24 小时唤醒 **2880 → 288**，**30 分钟兜底仍准点**：拍子变长只许省唤醒，不许推迟兜底 |
| 真机对照 | 改前 80 分钟发 51 次定位请求（每 75–94 秒）、gps 以 HIGH_ACCURACY 连挂 33 分钟、11 小时只落 8 个点；改后 40 分钟 **1 次**请求（30 分钟兜底，network 18ms 出点）、0 次订阅、门禁全程 SLEEPING |

## 明确不做

**地图匹配（snap-to-road）**：轨迹直接连折线，穿楼穿河照画。Strava / 高德 / 百度靠路网数据吸附，零第三方 SDK 约束下拿不到路网。这是**已接受的取舍**，不是待办。

## 覆盖口径：待机 ≠ 断档（真机校正）

门禁 `SLEEPING` 时静止不建订阅、只按 30 分钟兜底采一点（`LocationForegroundService.STILL_FALLBACK_MS`），点间距必然 ≈30 分钟，所以覆盖判定**不能用「2 × 静止间隔 = 6 分钟」**——真机 24 小时里 40+ 段 ≈30 分钟的兜底静默会被旧口径全画成断档。`record/CoverageTimeline.kt` 现分四档：有采样 / 省电待机（≤35 分钟 = 兜底 30 + 调度余量 5，**计入覆盖率分子**）/ 断档（35 分钟 ~ 2 小时）/ 深断档（≥2 小时）；2 小时与 `LocationGapHealing.DEEP_GAP_MS`（30 分钟）不同值也不同语义：那边是动作阈值（过阈值重建订阅），这边是呈现阈值（只决定分色与图例）。

## 真机标定（2026-10-30，HyperOS / Android 16，三权限全授予）

| 观测项 | 实测 | 结论 |
|---|---|---|
| provider 构成 | passive 2134 / network 38 / gps 4（近 8 天 2176 条） | 室内几乎全靠系统缓存；订阅派点只喂模式，落库走缓存兜底 |
| 精度分布 | 94% 落在 10–50m，无 500m+ | 精度够用；用户感知的「不准」来自点位抖动，不是点位很粗 |
| 静置误判 | 90 秒内 STILL↔MOVING 来回 4 次，订阅重建 5 次 | 已修：位移须超过两端精度之和（噪声地板，见 `LocationModeTracker.onSample`） |
| 修复后同口径 | 90 秒 0 次切换、0 次重建 | 探测点照常更新模式，落库仍按 180s 节流 |
| 功耗门禁（`MotionGate`） | 未确认远行时不再建订阅（手持态原先一直挂着 30s 高精度订阅，是耗电主因） | 三态：SLEEPING 不定位 / PROBING 只 180s 单点 / MOVING 才建 30s 订阅；心跳同步受门禁约束 |
| 显著运动注册（真机） | `registerListener` 静默失败（`E/SensorManager: Trigger Sensors should use the requestTriggerSensor`），退化后 30s 批量投递只剩 1 个样本、stddev 恒 0，门禁永不唤醒 | trigger 传感器只能用 `requestTriggerSensor`；注册失败必须打原因，不许静默降级 |

未验证：户外 GPS 冷启动 TTFF、室内 NETWORK 精度、HyperOS 长时（8h）后台存活；模拟器（emulator-5554，无步数计与显著运动传感器）只验退化路径：静止 100 秒 0 次订阅、抖动→`PROBING` 不建订阅、注入步态或 geo 位移→`MOVING` 建 gps 订阅、停走 5 分钟回 `SLEEPING` 且三 provider `-registration`。

## 验收口径（真机实测标定后才写进门槛）

调研给出的工程建议区间，**非厂商官方指标**，必须用自有机型先标定：

| 指标 | 口径 | 参考阈值 |
|---|---|---|
| 覆盖率（后台 8h / 24h） | 按 35 分钟分桶（待机兜底 30 + 余量 5），有点的桶 / 总桶；24h 另含息屏 + 切后台 + 一次手动杀进程 | 8h ≥95%、24h ≥98%，最长空洞 ≤35 分钟 |
| 空洞次数 | 连续缺口 > 35 分钟记一次（待机兜底静默不算缺口） | 24h 内 ≤2 次 |
| 静止误判率 | 静置 1h 的累计虚假里程 | <20 m，假移动占比 <5% |
| 轨迹偏移中位数 | 已知直线逐点垂距 | 开阔地 ≤5 m，城市峡谷 ≤15 m |
| 高精度点占比 | 全天 accuracy ≤50 m 的比例 | 室外 ≥80% |
| 首点时间 TTFF | 冷启动到首个 accuracy ≤50 m | 室外 ≤10 s |
| 单日耗电占比 | 连续 8h 息屏采集 | ≤5%（balanced+距离过滤）/ ≤15%（高精度） |

## 已修复的关键缺陷（防止回退）

`LocationQuality.confidenceOf` 曾把 `passive` 塞进 else 分支按「永不高置信」处理，而 `PROVIDER_PRIORITY` 又把 passive 排第一 → 系统缓存里 5 米的 passive 点永远判 LOW，模式判定永远拿不到双高置信点、永远停在 STILL。**精度分级只看精度，不看 provider 名**（network 除外）。
