# 事件采集扩容与每日行程（调研）

> 目标：App 侧收录更多事件 + 位置与地址 → 每日行程。系统类 11 种事件保持现状。
> 结论：都能做，成本集中在「后台定位授权」；App 侧页面轨迹零新权限、增量最大。

## 现状边界

| 能力 | 现状 |
|---|---|
| 前台 App | 1s 轮询取包名，只到 App 粒度（`APP_USAGE` 带时长） |
| 页面 | 不落库；`CONTENT_CHANGED` 只喂开屏跳过引擎 |
| 位置 | `LOCATION` 类型与 `LocationHandler` 已就绪，**无采集源、无定位权限** |
| 权限 | manifest 无定位 / 使用情况访问 / 通知使用权 |

## App 事件扩容（按性价比分层）

| 层 | 内容 | 新权限 | 增量 |
|---|---|---|---|
| P0 | 页面轨迹 `PAGE` | 无 | 最大：App 内到页面级 |
| P0 | `TYPE_WINDOWS_CHANGED` | 无 | 低：解释悬浮窗顶掉根窗口 |
| P1 | 通知摘要 `NOTIFICATION` | 通知使用权（1 步） | 中：谁在找你、哪类消息 |
| P1 | 点击/滑动聚合计数 | 无 | 低–中：页面活跃度 |
| P2 | 逐条点击/输入/焦点、MediaSession、截图 OCR | 各自 | 低 / 隐私高 |

- 页面粒度三路合并：①`WINDOW_STATE_CHANGED` 的 className（多 Activity App 有效，Compose 单 Activity 恒同类名）②窗口标题 ③节点文本指纹（轮询侧轻量抽取，限深 8、节点 200）。落库 `PAGE`：`ENTER`/`CHANGED` + `duration`，detail 存 `package_name`/`app_name`/`activity`/`page_key`/`title`/`source`/`clicks`/`scrolls`。
- 通知事件只存 `channel`/`title_len`/`text_len`/`category`/`ongoing`，正文不入库；`notificationTimeout=100` 使任何类型上限约 10 条/秒/包。
- UsageStatsManager（「使用情况访问」1 步）可回溯约 7 天、带 Activity className，用于补杀进程/冻结期缺口；写 `APP_USAGE` 时带 `source=usagestats`，与 `UsageTracker` 去重。
- 新增 type 会触发约 6 处 exhaustive `when`（色表/图标/筛选/目录）；`emit` 对未注册 handler 静默丢弃，注册要成对补。

## 定位与地址

| 方案 | 可用性 | 用不用 |
|---|---|---|
| `LocationManager` + `PASSIVE`/`getLastKnownLocation` | 有他人定位即有值，≈0 功耗 | 主路径 |
| `NETWORK_PROVIDER` | 室内可用，100–2000m | 兜底 |
| `GPS_PROVIDER` | 室外 5–30m，室内基本失败 | 仅兜底 |
| FusedLocation（GMS） | 国内无 GMS | 不引入 |

- 硬门槛是权限：Android 10+ 后台读位置须 `ACCESS_BACKGROUND_LOCATION`（HyperOS 约 6–8 步，含自启动、省电策略）；只有前台 FINE 时后台 `getLastKnownLocation` 返回 null。
- 采样寄宿已有 1 分钟 `AlarmReceiver`，10 分钟节流；`COORDINATE` 节流落库，`ENTER`/`EXIT` 由停留状态机产生。
- 逆地理：系统 `Geocoder` 只做 3s 探测（国内 OEM 后端不保证），失败只留坐标；主路径用已有后端上报时批量回填 `address`；离线 POI 库数百 MB，不采用。
- 隐私：默认关；本地 lat/lng 3 位（≈110m）、address 到区/街道；上报 2 位；LOCATION 90 天清理、不进互传与备份。

## 每日行程

- 形态：`records` 的**派生视图**，不建表。段 = `Stay`（地点+停留）/ `Move`（移动）/ `Gap`（未记录，不猜）。
- 无定位版（先做）：SSID 连续 ≥10min = 地点，切换 = 地点变更；`APP_USAGE` 间隔 ≤5min 合并成使用簇 = 停留。缺距离与移动方式，同 SSID 分不出家与公司。
- 定位版：精度 >100m 的点丢弃，坐标量化 0.001°；连续 ≥10min 且质心半径 ≤80m 判停留；两点间净位移 >300m 且覆盖 ≥60% 判移动。
- 抗定位漂移：单点的前后相邻都在 80m 外、而这两点彼此 ≤120m（1.5 倍停留半径）→ 判漂移点、剔除后再聚类。首尾点不参与判定；邻居取原始序列，所以连续异常点不连坐（两个连续同址的假点彼此 0m，按真实换址处理）。
- 同址合并：相邻两段停留之间没产出 Move、且地点登记表判为同一地点 → 合成一段（start 取前段、end 取后段），期间 App 使用重算后合并去重。真实换地点会先产出 Move，因此不会被合并。
- Gap 分两级（`GapReason`）：区间内没有定位采样 = `INTERRUPTED`（采集中断 / 窗口端头）；有采样仍判不出 = `UNRESOLVED`（漂移、>1h 断档、覆盖 <60%）。DEVICE 基准恒为 `INTERRUPTED`。
- 计算时机：打开页面现算（当日 <50ms）+ 进程内 LRU；周/月趋势再上日终批量。
- UI：概览「今日」新增时间带 `TimelineBand`（Canvas 自绘 24h 一轴），点段看期间 Top3 App；不加 Tab（Tab 下标被通知深链依赖）。

## 分期建议

1. **阶段一（零新权限）**：`PAGE` 页面轨迹 + `WINDOWS_CHANGED` + 无定位版行程 —— 可独立交付。
2. **阶段二**：定位 L0/L1（坐标 + 停留识别 + 设置页权限自检与引导）。
3. **阶段三**：后端逆地理回填 + 通知摘要 + UsageStats 对账。

## 落地（2026-10-23，指纹档）

- 粒度定在**指纹档**：`PAGE` 只存 `package_name`/`app_name`/`page_key`/`source`/`duration_ms`；页面文本只在内存参与 hash，不进库。四档粒度与按 App 分档未实现（原型 `s16`/`s17` 保留设计）。
- 采集：`record/PageTracker.kt`（指纹状态机，轮询限深 8 / 节点 200 / 文本 20 条）、`record/LocationCollector.kt`（PASSIVE→NETWORK→GPS，30min stale、100m 精度、10min 节流）。
- 聚合：`domain/.../trip/TripAggregator.kt`，打开页面现算，不建表。
- UI：概览「今日行程」卡 + `ui/trip/TripScreen.kt`（`AnimatedScreenOverlay` 二级页，不占 Tab）。
- 顺带修正：`LiveModels.startOfDay` 由「UTC 零点」改为系统时区零点——原实现使「今日」窗口从本地 08:00 起，概览 KPI 与行程都丢凌晨时段。

## 未验证（真机再定）

- HyperOS 的 `Geocoder` / `NETWORK_PROVIDER` / 前台服务后台启动豁免。
- 微信、小程序、Compose App 的节点文本可读性 —— 决定页面轨迹覆盖度。
- UsageStats 在 HyperOS 的保留天数与入口位置。
