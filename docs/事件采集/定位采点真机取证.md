# 定位采点真机取证

> 何时读：验收「静止不采点」「兜底窗口」「服务被杀后自愈」三类改动的真机证据，或要复跑同一套观测。结论：静止段、退后台段、失败重试闭环、锚点回填均真机实证；走动段半实证；壳化自愈仅单测。三轮观测：22:33→23:50（77 分钟，USB 断开提前结束）、22:33→23:48（跨一次进程被杀）、22:08→22:26（装新包验锚点回填）。

## 第二轮：跨进程被杀的兜底锚点缺陷（22:46→23:48）

| 时刻 | 事件 | 证据 |
|---|---|---|
| 22:34:21 | 进程被 MIUI `SwipeUpClean` 杀掉 | `logcat -b events`: `am_kill ... SwipeUpClean`；`am_schedule_service_restart` 排了重启 |
| 22:46:05 | **服务已死期间**心跳采到一个真点 | 库里 LOCATION（network，55m）；`logcat -b system` 22:46:03 `sending alarm ... AlarmReceiver` |
| 23:13:01 | 用户解锁开 App，服务才被拉起 | `SCREEN UNLOCKED` 23:12:58；`门禁 ticker：下一拍 300s（启动，SLEEPING）` |
| 23:18:01 | 首拍见锚点=0 → 记起点、不采点 | `LocationTickerPolicy.nextDelayMs` 只有 `lastFallbackAtMs<=0` 才返回 5 分钟 |
| 23:43:01 | 算出 remaining=299s，仍未到期 | `1800 - 1500 = 300`，与日志逐值吻合 |
| 23:48:01 | 兜底终于触发，采到点 | `lastOpTime=23:48:01.423`；库里新增 network 点（30m） |

**代价**：22:46:05 → 23:48:01 共 **62 分钟零定位**，充电档设计值是 30 分钟。真因是兜底锚点 `LocationGateState.lastFallbackAtMs` 纯进程内、被杀即归零，而心跳的 `NOT_RUNNING` 分支采点后不写锚点。

**修法与边界**：`LocationTickerPolicy.anchorSeedMs` + `LocationGateState.seedFallbackAnchor`，进程启动时用库里最近一条 LOCATION 回填（复用 `LocationSuccessSeed` 的同一次查库，IO、只跑一次）。锚点语义是「兜底**发起**」，库值给的是「**成功**落库」，差几秒、方向偏早（多发一次探测而不是漏点），**取较早值**不回拉。被质量闸拒掉未落库的兜底无法回填，最坏退化回旧行为。

## 第三轮：锚点回填修复的真机验证（22:08→22:26）

| 时刻 | 事件 | 证据 |
|---|---|---|
| 21:55:37 | 库里最后一条 LOCATION（network，30m） | 修复前的旧包采的 |
| 22:08:50 | 装新包后冷启动，服务 onCreate 跑回填 | `门禁 ticker：下一拍 300s（启动，SLEEPING）` |
| 22:09:00 | 回填生效 | `fallbackAnchorAgeSec=803`，`lastSuccessAgoSec=803` 两处同值 |
| 22:25:37 | 兜底触发（装上后 16 分钟就到期） | `门禁 ticker：下一拍 106s`；22:25:38 落库 LOCATION 40→41 |
| 22:26:24 | 锚点随兜底刷新 | `fallbackAnchorAgeSec 1786 → 46`，`fallbackMin` 保持 30 |
| 21:55:37→22:25:37 | **30 分钟窗口只发起 1 次定位请求** | `opCount` 全程 17 不变，`lastOpTime` 只在 22:25:37.376 翻页（network `+registration` 30 秒后 `-registration`） |
| 22:28→22:30 | 兜底后的静止段零射频 | 90 秒内 `opCount 17 → 17`，无任何 provider 注册 |

锚点回填到 21:55:38、兜底精确落在 21:55:37+30min = 22:25:37 —— 与 `fallbackAnchorAgeSec=1793` 时报文里的到期点逐秒吻合。**若沿用旧行为**（锚点为 0 → 首拍 22:13:50 记起点），兜底要到 22:43:50 才发生，本次提前 18 分钟，即修复目标的直接量化。观测字段 `fallbackAnchorAgeSec` 为本次新增（`DebugCommandReceiver`），没有它无法在真机上区分「回填跑了」与「锚点仍是 0」。

## 走动段（半实证）

22:23→22:34 采样节奏 `177s → 185s → 40s → 30s → 31s → 30s → 37s → 31s → 30s`，从静止档 180s 切到 30s，同期 `dumpsys location` 出现 fused + network 的 30 秒 BALANCED 注册 —— 门禁确实在位移后升级并建订阅。**缺**：没有独立步数证据，无法区分「位移升级」与「被动点连带升级」；探测退避阶梯 180/300/600s 仍只有 `MotionGateTest` / `MotionGateProbeBackoffTest` / `MotionGateMovingKeepTest` 覆盖。

## 观测方法（可复跑）

```bash
ANDROID_SERIAL=63caad7a INTERVAL=120 DBAGE_INTERVAL=600 OUT=/tmp/gps-timeline-v4.tsv /tmp/gps-sample.sh
ANDROID_SERIAL=63caad7a /tmp/gps-sample.sh once     # 单次采样
/tmp/gps-dbage.sh                                   # 库里最近一条 LOCATION 距今分钟
```

列：`wall procLastSuccessAgoSec dbLastLocAgeMin charging serviceHealth gate tickerIdleSec startForegroundCount foregroundAlive fallbackMin isForeground fgTypes svcStartFgCount lmsLines opCount lastOpTime passiveN netN gpsN fusedN`。`opCount` 与 `lmsLines` 的区间增量才是「有没有发起定位」的直接证据；`dbLastLocAgeMin` 标 `~` 的是沿用上值（每 10 分钟才真查一次，避免取证广播扰动样本）。

**查「有没有发起定位」别数总行数**：注册与注销会让计数**减少**，只有「末尾行的时刻变了」或区间增量才是证据 —— 第一版判定写成「计数 > 基线」导致白等 10 分钟。

## 已知残留（未修）

- **`enterForeground()` 静默失败**：`LocationForegroundService.kt:406` 的 `if (!enterForeground()) return START_NOT_STICKY` 把异常吞成 `Log.w`（:1172-1178），`START_STICKY` 排了重启也拉不起来。修法涉及 `ForegroundServiceStartNotAllowedException` 重试，与锚点记账是两件事。
- **22:46→23:13 为何只有 1 个点**：`LocationActiveFixGate` 与 `LocationThrottle` 都允许每 3 分钟一次，与 27 分钟 1 点不符；需要那段的 `AlarmManager` 心跳计数才能定性是「没到点」还是「到点被节流」。
- `lastSuccessAtMs` 回填（`LocationSuccessSeed`）与 debug `bypass_throttle` 新建实例导致健康统计分叉（已修，`LocationCollector.adoptSample` 回写）属前一轮结论。
