## 1. 结论速览（TL;DR）

本模块的架构方向（无障碍服务 + 选择器 DSL + 规则表）与业界主流（GKD）一致，**但触发链路、选择器能力、规则数据三处关键实现缺失，导致规则引擎在绝大多数启动中根本没有参与匹配**；现有的"跳过成功"记录主要来自返回键/盲点连点等兜底手段，属于假成功。

> ✅ **2026-10-13 已按 §4 实施完毕**（P0-1~P0-4 + P1-1 订阅 + P1-2 快照导出器，152 个单测全绿，
> 真机验证见文末「实施进展」）。剩余未做项：订阅/快照的 UI 入口、订阅定时检查、逐 App 规则实测调优。
> 代码现状以 [设计](设计.md) 为准。

| # | 结论 | 证据 |
|---|------|------|
| 1 | 启动瞬间 `rootInActiveWindow` 常为 null，且当前实现**不重试**，整次启动直接漏检 | 真机日志：`handleWindowChange: rootInActiveWindow is null for com.taobao.idlefish` |
| 2 | 是否检测开屏绑定在"包名变化"这一次性判断上，且与 1s 轮询抢 `lastPackageName`，一旦错过就再无机会 | `MonitorAccessibilityService.kt:173` + 日志中闲鱼 4 次 window 事件只处理了第 1 次 |

| 4 | `matchDelay` 用"每次扫描取消上一次延迟任务"实现，广告页 CONTENT_CHANGED 连续到来时规则**整个窗口一次都没执行** | 真机日志：拼多多 5s 监控窗口内 0 次规则匹配 |

| 8 | 规则语法超出引擎能力：`[text.length<10]` 等成员表达式不支持，且**静默不匹配** | `NodeMatcher.kt:244-263` 无 `text.length`；知乎规则即含该表达式 |
| 9 | 选择器解析器只支持"标签 + `[]` 简化表达式"，无 `|| && !( )` / `@` / 关系算子 / 成员表达式 | `SelectorParser.kt:27-190` |
| 10 | 快速查询只对 `[id=]`/`[text=]` 生效，`[text*="跳过"]` 走全树 DFS，实测单选择器 ~200ms、4 个选择器阻塞主线程 800ms | `NodeMatcher.kt:110-127`；日志 `GenericIdInterceptor` 03.627 → `TextMatchInterceptor` 04.423 |

## 2. 业界主流做法（外部来源）

### 2.1 GKD（43k★，本模块的对标对象）

| 机制 | 做法 | 可借鉴点 |
|------|------|---------|
| 事件 | 只订阅 `typeWindowContentChanged|typeWindowStateChanged`，`notificationTimeout=100`，**contentChanged 100ms 节流**，单线程消费、单飞（querying） | 我们的节流一致，但缺少"单飞 + 新事件打断旧匹配" |
| 匹配起点 | 默认从**事件节点**（`event.source`）开始匹配，`matchRoot=true` 才整树；事件过快退化为 root | 我们每次都整树 DFS，慢且易漏 |
| 查询优化 | 末尾属性选择器首表达式为 `[id=]/[vid=]/[text=]/[text^=]/[text*=]/[text$=]` 且 `fastQuery/quickFind` 为真时，改用 `findAccessibilityNodeInfosByViewId/ByText`；`[parent=null]` 直接视为根 | 官方量化：3 次 API 调用 ≈ 99 次节点判断 |
| 规则闸门 | `matchTime`（参与匹配窗口，开屏=10000ms）、`actionMaximum`、`actionCd`(默认 1000)、`resetMatch`(activity/match/app)、`actionCdKey/actionMaximumKey`（多条开屏规则共享计数）、`preKeys`（顺序链）、`priorityTime/forcedTime` | 我们的 5s 窗口 + 全局固定冷却过于粗糙 |
| 动作语义 | `click` 默认：可点击→`clickNode`，否则→`clickCenter`；`clickCenter` 按节点中心派发手势；`position` 自定义坐标；`back` 是**用户显式配置**的动作，不是兜底 | 返回键必须是"规则动作"，不能当默认兜底 |
| 作用域 | `activityIds`/`excludeActivityIds` **前缀匹配**，为空=全界面生效；全局规则组另有 `matchLauncher=false` | 我们反过来：className 不含 splash 关键词就锁死高危策略 |
| 选择器 | 属性成员表达式（`text.length`、`width`、`childCount`…）、运算符 `= != > >= < <= ^= !^= *= !*= $= !$= ~= !~=`、逻辑 `|| && !( )`（并列 `[]`=`&&`）、`@` 指定点击目标、关系算子 `> + - <<`、从右往左求值 | 我们要支持 GKD 选择器子集，否则无法复用任何现成规则 |
| 订阅 | JSON5 单文件全量：`{id,name,version,checkUpdateUrl,supportUri,categories,globalGroups,apps}`；`checkUpdateUrl` 只返回 `{id,version}` 做轻量比对 | 规则可持续更新，是长期成功率的关键 |

### 2.2 GKD 官方"开屏广告"全局组（最经典的通用规则）

```json5
{ key: 0, name: '开屏广告', actionMaximum: 2, matchTime: 10000, resetMatch: 'app',
  actionCdKey: 0, actionMaximumKey: 0,
  rules: [
    { key: 0, quickFind: true,
      matches: '[text*="跳过"][text.length<10][visibleToUser=true]' },
    { key: -1,
      matches: '[childCount=0][visibleToUser=true][(text.length<10&&(text*="跳过"||text*="跳過"||text*="skip"||text*="Skip")) || id$="tt_splash_skip_btn" || vid*="skip" || vid*="Skip" || (vid*="count" && vid*="down" && vid!*="download") || desc*="跳过" || desc*="skip"]' },
  ] }
```

**要点**：跳过按钮的通用特征 = 文本含"跳过/skip" + `text.length<10` + 可见 + **`childCount=0`（叶子节点）**；无文本时退化为 `vid*="skip"`、`vid*="count"&&vid*="down"`、`desc*="跳过"`。

### 2.3 真实 App 规则（AIsouler 订阅，724 个 App；仅借鉴写法，不可直接用其数据）

```ts
// 京东 / 抖音 / 拼多多（一字不差）
'[text*="跳过"][text.length<10][width<500 && height<300][visibleToUser=true]'
// 淘宝
'@[vid*="close"] > [text*="跳过"][text.length<10][width<500&&height<300][visibleToUser=true]'
// 小红书
'[text*="跳过" || text^="Skip Ad"][text.length<10][!(vid="tv_user_name")][visibleToUser=true]'
'[vid="splash_count_down_view"]'
// 哔哩哔哩（注释原文：[text*="跳过"] 会误触搜索框）
'[vid="count_down" || vid="skip"][visibleToUser=true]'
// 美团
'TextView[text*="跳过"][text.length<8][clickable=true]'
// 淘特
'[id="com.taobao.litetao:id/root_layout"] > TextView[text^="还剩"&&text$="秒"]'
// 山姆会员商店（无文本，靠结构）
'@ImageView[clickable=true] <2 [id="cn.samsclub.app:id/advertising_container"]'
```

> 结论：**主流 App 的跳过按钮基本没有稳定 id/vid**，可靠特征是"文本含跳过 + 短文本 + 小的可见叶子节点"；纯图标按钮只能靠结构关系或坐标。误触主因是首页搜索框/搜索页，靠 `excludeActivityIds`/`excludeMatches` 排除。

## 3. 本模块现状与差距（含真机证据）

### 3.1 触发链路

| 现状 | 位置 | 问题 |
|------|------|------|
| `shouldCheckSplash = packageName != lastPackageName` | `app/src/main/java/com/bsfeng/monitor/service/MonitorAccessibilityService.kt:173` | 一次性判断；`lastPackageName` 由 1s 轮询线程更新，二者竞态；同包名后续 window 事件（真正的广告 Activity）不再检测 |
| root 为 null 直接放弃 | 同上 :178-198 | 启动瞬间常见，没有重试也没有转入监控 |
| 监控 5s | `app/src/main/java/com/bsfeng/monitor/skip/SkipRuleEngine.kt:104` | 业界 `matchTime=10000`；弱网/慢机型不够 |
| 熄屏不区分 | 同上全文件 | Dozing 期间仍在点按/返回，产生假记录与误操作 |

### 3.2 规则执行

- `canRunFullChain = isSplash || hasExplicitMatch`（`SkipRuleEngine.kt:203-208`）：`isSplash` 靠 className 含 `splash/AdActivity/开屏/广告`，真机实测从未命中（`IndexActivityV2`/`MainFrameActivity`/`MainActivityV2`/`doubao...`）；`hasExplicitMatch` 仅 4/99 组满足 → **文本兜底、坐标兜底对所有其它 App 全部失效**。
- `matchDelay` 饥饿：`executeRule` 每次调用都 `removeCallbacks` 上一个延迟任务（`SkipRuleEngine.kt:253`），而 CONTENT_CHANGED 驱动的扫描比 500ms 更快 → 延迟任务被无限推迟，窗口内 0 次执行。
- 假成功：`GlobalBackInterceptor`（`AdInterceptors.kt:79-83`）与 `tryCoordinateClick`（`SkipRuleEngine.kt:406-463`）返回 true 即写 `AD_SKIPPED`，`SkipEventRecorder.recordSkip(pkg, name, "", className)` 的 selector 恒为空 → 无法区分真跳与误触。
- 性能：`NodeMatcher.findLeaf` 只对 `[id=]`/`[text=]` 用原生 API；`[text*="跳过"]` 走整树 DFS（`NodeMatcher.kt:110-127`），实测 4 个通用 ID 选择器耗时 800ms，阻塞无障碍主线程。

### 3.3 规则数据

- `app/src/main/java/com/bsfeng/monitor/skip/BuiltInRules.kt`：99 条规则 / 237 个选择器，其中 `[text*="…"]` 115 个、`[id$="…"]` 99 个、`[vid*="…"]` 12 个；**只有 4 个规则组带 `activityIds`**；无 `excludeMatches`/`excludeActivityIds` 概念。
- 本机规则快照：`/data/data/com.bsfeng.monitor/files/skip_rules.json`（`skip_rule_prefs.xml` 中 `built_in_version=6`）。
- 规则语法越界：`[text.length<10]` 在引擎中恒不匹配（`NodeMatcher.kt:244-263` 只认固定属性名）。
- 官方/AIsouler 订阅均已停更；活跃的是 [Lin-arm/GKD_subscription](https://github.com/Lin-arm/GKD_subscription)（5.9k★，每日构建）。**三者均无 LICENSE 文件 → 规则数据不可直接内置**，只能借鉴写法或让用户自行添加订阅 URL。

## 4. 改进方案

### P0-1 修复触发链路（收益最大，改动最小）

1. `MonitorAccessibilityService.handleWindowChange`：包名变化后**不再依赖一次性判断**——只要前台包名与当前监控目标不同即进入"启动窗口"监控；root 为 null 时改为立即 `startWatching`（由监控循环去拿新鲜 root），而不是放弃。
2. 监控窗口 5000ms → 10000ms（对齐 GKD `matchTime`），并把窗口内扫描改为"事件驱动 + 300ms 兜底"。
3. 熄屏/锁屏（`PowerManager.isInteractive == false` 或 `KeyguardManager.isKeyguardLocked`）时丢弃事件、禁止一切点击动作。

**验收**：冷启动 10 次目标 App，日志中 `onWindowChanged` + 监控扫描均出现（当前闲鱼这类会 0 次）；熄屏期间不再产生 `AD_SKIPPED`。

### P0-2 消灭假成功

1. 删除 `GlobalBackInterceptor` 的默认兜底（返回键只能由规则 `action: "back"` 显式使用）。
2. `tryCoordinateClick` 只在"命中广告容器/跳过候选节点"后才允许，且只点右上角 1-3 个位置；每个 App 每次启动最多一次。
3. `SkipEventRecorder.recordSkip` 必须带上真实命中的 selector；只有"点击后验证阶段确认广告消失"才写 `AD_SKIPPED`。

**验收**：`AD_SKIPPED` 记录 `selector` 非空率 = 100%；正常页面零点击、零返回键。

### P0-3 规则执行不再被饿死

- `matchDelay` 改为独立队列（延迟任务不再被扫描取消，或被扫描复用同一 deadline）；`matchRoot`/`actionDelay` 语义按 GKD 落地。

**验收**：拼多多这类 CONTENT_CHANGED 密集场景，10s 窗口内规则匹配次数 ≥ 5。

### P0-4 选择器引擎补齐 GKD 语法子集

在 `app/src/main/java/com/bsfeng/monitor/skip/SelectorParser.kt` + `NodeMatcher.kt` 中实现：

1. 属性成员表达式：`text.length`、`width`、`height`、`childCount`、`index`、`depth`（`NodeMatcher.getAttributeValue` 扩展）。
2. 运算符全集：`= != > >= < <= ^= !^= *= !*= $= !$=`；`null` 值语义（除 `= !=` 外为 false）。
3. 逻辑表达式：`||`、`&&`（优先级高）、`!(...)`；并列 `[a][b]` ≡ `[a&&b]`。
4. 目标节点 `@`（默认最后一个属性选择器）。
5. 关系算子：`>`、`+`、`<<n`（后代链），从右往左求值。
6. 快速查询：`[vid=]`/`[id=]` → `findAccessibilityNodeInfosByViewId`；`[text*=]/[text^=]/[text$=]` → `findAccessibilityNodeInfosByText`（Android 该 API 本身是包含匹配）再过滤；兼容 `fastQuery` 与 `quickFind` 两种键名。

**验收**：`./gradlew test` 新增解析/匹配用例全绿；237 个内置选择器 100% 可解析（`BuiltInRulesTest` 结构校验）；单次匹配耗时 < 50ms。

### P1-1 规则数据结构对齐 GKD（含订阅）

- 规则模型增加：`globalGroups`、`anyMatches`、`excludeMatches`、`excludeActivityIds`、`matchTime`、`resetMatch`、`actionCdKey`、`actionMaximumKey`、`preKeys`、`fastQuery`、`matchRoot`、`action(position/back/longClick)`。
- 内置规则改为"**1 个全局开屏组（自研，写法借鉴 §2.2）+ 少量自研 App 规则**"；主力 App（本机已装：淘宝特价版/闲鱼/小红书/美团/抖音/B站/拼多多/高德/百度地图/中国移动/12306/贝壳/携程/平安好车主…）逐个人工实测补规则。
- 新增订阅拉取（`HttpURLConnection`，零第三方依赖）：`checkUpdateUrl` 轻量比对 → 全量替换；用户自行添加订阅 URL 以规避第三方规则 LICENSE 风险。

**验收**：修改订阅版本号后 App 内自动更新生效；订阅失败静默降级到内置规则。

### P1-2 快照工具

导出当前前台页面无障碍树 JSON（`SnapshotExporter`），用于写规则时验证选择器。当前 `NodeMatcher.diagnosePageStructure` 是空桩（`NodeMatcher.kt:266-269`），先落地为"结构摘要日志"。

### P2（可选，需产品决策）

- 截图 + 区域兜底（Touch-Helper 路线）：成本低但需按 App 维护坐标；
- OCR / YOLO / VLM（ad-skipper 路线）：成功率最高，但与"零第三方业务依赖"原则冲突，且耗电/体积代价大。
