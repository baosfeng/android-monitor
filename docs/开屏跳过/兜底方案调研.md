## 1. 问题界定

### 1.1 哪些框架/场景属于「无障碍树里拿不到文本与稳定 ID」

**先说机制**：Android 的无障碍树由 View 层级 + `AccessibilityNodeProvider` 暴露的虚拟节点构成；渲染到**独立绘制表面（Surface / GL / Vulkan）**的内容不产生子 View，自然也没有可读节点。【官方源码/官方文档】Android 无障碍以 `AccessibilityNodeInfo` 暴露节点、虚拟视图须由 `AccessibilityNodeProvider` 主动 populate。

按框架逐一核实（**注意：结论与「想当然」不同**）：

| 框架/形态 | 无障碍树里到底有什么 | 证据 |
|-----------|---------------------|------|
| **Flutter** | 语义树由引擎的 `AccessibilityBridge` 控制，其开关就是系统无障碍开关：`isAccessibilityEnabled() { return accessibilityManager.isEnabled(); }`，且在无障碍关闭时事件**直接 return**。节点属性固定为 `setClassName("android.view.View")`、`setViewIdResourceName(semanticsNode.identifier)`（App 自己给的 identifier，多数为 null/空）。文本由 role configurator 按控件 role 写入 | 【官方源码】flutter/flutter `engine/src/flutter/shell/platform/android/io/flutter/view/AccessibilityBridge.java`（本次直接抓取源码核对：`isAccessibilityEnabled()`、`setClassName`、`setViewIdResourceName`、`setVisibleToUser(true)`、`if (!accessibilityManager.isEnabled()) return;`） |
| **Flutter 的推论** | ⚠️ **「Flutter 开屏一定拿不到文本」是错误前提**：只要 App 给控件加了语义标注（`Text` 之类默认就带 label），无障碍开启后就能读到文本。真正读不到的情况是：①广告用 `ExcludeSemantics`/未标注的自绘控件 ②开屏广告是原生广告 SDK 的图片 View ③按 `identifier` 找不到稳定 ID（Flutter 页几乎**没有稳定资源 ID**，这点是确定的） | 【官方源码】同上 + 【推断】 |
| **Unity** | Unity 6.3 的 Accessibility 模块**默认启用**，节点映射到 `android.view.accessibility` 的 `AccessibilityNodeInfo`（官方原文：Android 侧 native node representation = `AccessibilityNodeInfo`）。但需要**开发者创建可访问性元数据**（节点、role、label） | 【官方文档】[Unity Manual 6.3 — Introduction to the Accessibility module](https://docs.unity3d.com/6000.3/Documentation/Manual/accessibility/module-intro.html) |
| **Unity 的推论** | 广告 SDK 在 Unity 里渲染的开屏页通常不会为「跳过」按钮建 a11y 元数据 → 树里无文本。**这是推断，未采样验证** | 【推断】 |
| **WebView** | Chrome/WebView 的无障碍「off by default and enabled automatically on-demand」（官方原文） | 【官方源码】chromium/chromium `docs/accessibility/browser/android.md`（本次通过 GitHub 镜像抓取核对：第 226 行起） |
| **WebView 的推论** | 无障碍开启后 WebView 会构建 a11y 树；若跳过按钮是 `<img>`/canvas/背景图（无 alt、无文本节点）则读不到文本；若页面上有 `<a>跳过</a>` 这类文本节点则**能**读到。⚠️ 所以 WebView 必须**按页面实测**区分，不能整体归为「读不到」 | 【推断】 |
| **纯图片按钮（原生）** | 原生 `ImageView`/`ImageButton` 若无 `contentDescription`，节点存在但 `text`/`desc` 皆空；若还不可点击（点击由外层容器处理），则只有几何特征可用 | 【推断】 |
| **游戏引擎/自绘（含部分 Unity 老版本）** | 整页只有 `SurfaceView`/`TextureView`/`GLSurfaceView` 这类单节点 | 【推断】（Surface 不产生子 View 是机制结论，但「某 App 是否如此」需采样） |

**本项目已有的、可佐证「业界确实主要靠文本」的证据**：内置全局规则的选择器就是「文本含跳过 + 短文本 + 可见叶子节点」与少量固定 ID —— 见 `app/src/main/java/com/bsfeng/monitor/skip/BuiltInRules.kt`（`TEXT_SKIP` / `DESC_SKIP` / `VIEW_ID_SKIP`）。同一文件里唯一确认的广告 SDK 命名特征是字节系穿山甲的 `tt_splash_skip_btn`。【实测-本机】

### 1.2 可复现的判定方法（不靠猜）

> 下面这套流程是**给后续实施者的操作手册**，本次调研**未执行**（本任务不允许用 adb / 装 APK）。执行前请先读 [设计](设计.md) 与 [业界调研与改进方案](业界调研与改进方案.md)。

**步骤**

1. **确认「跳不过」**：设置页打开调试模式，冷启动目标 App，过滤日志
   ```bash
   ~/android-platform-tools/adb logcat -s SkipRuleEngine SkipAction MonitorDebug MonitorTimeline
   ```
   若出现 `SkipEngine: 未命中任何规则 <包名> / <Activity>`，即进入下一步。
2. **采集快照**：规则页「页面快照」（延迟 5 秒导出**当时前台页面**的无障碍树）→ `files/snapshots/<时间戳>.json`。
   导出字段（见 `app/src/main/java/com/bsfeng/monitor/skip/SnapshotExporter.kt`）：`id / vid / name / text / desc / clickable / longClickable / focusable / checkable / checked / editable / visibleToUser / left / top / right / bottom / width / height / childCount / index / depth`（字符串为空则省略该键，布尔与几何属性恒定输出）。【实测-本机】
3. **按判定表分类**（下表阈值是**建议初值，属推断**，必须用真实样本校正）：

| 类别 | 快照特征（可用弱信号） | 现有引擎能否跳过 | 需要的兜底方向 |
|------|----------------------|----------------|--------------|
| **A 有文本** | 存在 `text`/`desc` 含「跳过/skip」且 `childCount=0`、`visibleToUser=true` 的节点 | 能 | 无需兜底（属 P2-1 规则调优） |
| **B 无文本但有稳定 ID** | `vid`/`id` 形如 `*skip*`、`*count*down*`、`tt_splash_skip_btn` | 能 | 补 ID 规则（P2-1） |
| **C 弱信号可判** | 无文本无 ID，但存在「小块 + `clickable=true` + 右上角」节点；或整页节点数极少（< 5） | **不能**（写不出可靠选择器，也不敢点） | §2.1 弱信号启发式 / §2.3 坐标候选 |
| **D 像素渲染** | 根节点 `childCount` 极小（1~3），子节点 `name` 为 `SurfaceView`/`TextureView`/`GLSurfaceView`/`android.view.View`（Flutter），或整页只有一个接近全屏的 `ImageView` | **不能** | §2.2 截图启发式 / §3 OCR |
| **E 广告在独立 window** | `getWindows()` 里出现额外的应用 window（当前引擎只看 `rootInActiveWindow`） | 不能（未枚举窗口） | §2.1 第 4 条多窗口枚举 |

**建议初值（推断，需校正）**：「小块」= 节点面积 < 根节点面积的 1/9；「右上角」= `left > 0.6×屏宽 && top < 0.2×屏高`；「节点数极少」= 全页可见节点 ≤ 5。
现有代码里已有一处可复用的几何判据：**面积守卫**（命中节点面积 ×3 > 根节点面积即丢弃），见 `app/src/main/java/com/bsfeng/monitor/skip/RuleNodeFinder.kt`（`isOversized`）。【实测-本机】

### 1.3 可用的弱信号清单（全部已在选择器引擎里支持，**无需改引擎**）

下表属性名均可直接写进规则选择器（求值实现见 `app/src/main/java/com/bsfeng/monitor/skip/ExpressionEvaluator.kt`，属性表在 `getAttributeValue`）。【实测-本机】

| 信号 | 选择器写法示例 | 为什么可能有用 | 误点风险 |
|------|--------------|--------------|---------|
| 控件类名 | `[name="android.widget.ImageView"]`、`[name="android.view.SurfaceView"]` | 识别「像素渲染类」页面、识别图片按钮 | 低（判定用） |
| 子节点数 | `[childCount=0]`、`[childCount<2]` | 跳过按钮几乎都是叶子；整页节点少说明是广告页 | 低 |
| 可点击性 | `[clickable=true]` | 过滤装饰性图片 | 中（大面积可点击容器会误命中，需配合面积/尺寸约束） |
| 屏幕坐标 | `[left>648][top<216]`（**绝对像素**，需按分辨率维护） | 跳过按钮位置先验（右上角） | 中~高（分辨率/DPI/横竖屏会失效） |
| 尺寸 | `[width<500&&height<300]` | 小块约束（内置规则已在用） | 低 |
| 层级 | `[depth<3]`、`[index=0]` | 广告容器结构简单 | 低 |
| 可见/可用 | `[visibleToUser=true][enabled=true]` | 排除不可见占位节点 | 低 |
| 资源 ID | `[vid*="skip"]`、`[id$="tt_splash_skip_btn"]` | 广告 SDK 固定命名 | 低 |
| 文本/描述 | `[text*="跳过"]`、`[desc*="跳过"]` | 现状主路径 | 低 |
| 父/子关系 | `[parent.getChild(0).childCount=0]` | 从容器定位唯一子节点（山姆类结构） | 低 |
| 包名 | `[package="com.xxx"]` | 区分宿主 App 与广告容器 | 低 |

**改规则不需要改代码**：新增/覆盖内置规则 → `app/src/main/java/com/bsfeng/monitor/skip/BuiltInRules.kt`（改内容要递增 `BUILT_IN_VERSION`，当前为 8）；用户自定义规则 → 规则页（`app/src/main/java/com/bsfeng/monitor/ui/SkipRuleScreen.kt`）。

## 2. 零依赖可做的增强（不破「零第三方业务依赖」原则）

> 本节方案都不新增第三方库。但请注意：**「零依赖」不等于「零成本」**，成本主要是自研工程量、维护腐烂与实测调参。

### 2.1 纯无障碍弱信号启发式

| # | 启发式 | 落地方式 | 代价 / 误点风险 | 证据等级 |
|---|--------|---------|----------------|---------|
| 1 | **小块可点击节点 + 右上角区域**：`[clickable=true][childCount=0][visibleToUser=true][left>0.6W][top<0.2H][width<500&&height<300]` | 直接写内置规则（无需改引擎） | 误点风险中：右上角也可能有「关闭」以外的正常控件（如个人中心入口）。需配合时间窗口（`matchTime`）+ 只执行一次 + 点击后确认 | 【推断】 |
| 2 | **「广告容器」页面判定**：全页可见节点数极少（≤5）且存在接近全屏的 `ImageView` 或子节点 `childCount` 极小 | 需要引擎在扫描时提供「当前页面结构摘要」→ 属**改引擎**。已有现成基础可复用：`app/src/main/java/com/bsfeng/monitor/skip/NodeMatcher.kt`（`diagnosePageStructure`）与 `app/src/main/java/com/bsfeng/monitor/skip/SnapshotExporter.kt`（`summarize`） | 工程量中等；判据会随广告改版失效 | 【推断】 |
| 3 | **像素渲染类页面识别**：根节点子节点 `name` ∈ {`SurfaceView`、`TextureView`、`GLSurfaceView`}，或 `className=android.view.View` 且无 `text`/`desc`/`vid` | 同上，属**改引擎**（只用于「决定是否启用兜底层」，不直接点击） | 工程量小；这是**判定**手段，不是跳过手段 | 【推断】 |
| 4 | **多窗口枚举**：`AccessibilityService.getWindows()` 枚举交互窗口，广告以独立 window 呈现时能拿到它的根节点 | 服务配置已含 `flagRetrieveInteractiveWindows`（`app/src/main/res/xml/accessibility_service_config.xml`），能力已具备；引擎目前只用 `rootInActiveWindow`，需扩展 | 工程量中等；可能引入重复命中（同一按钮在多个 window 里出现） | 【实测-本机】配置可证；【推断】收益 |
| 5 | **包名/Activity 先验（仅用于排除）**：把「正常页面误点」风险高的界面加入 `excludeActivityIds`/`excludeMatches` | 直接写规则 | 低 | 【官方源码/真机】业界调研 §3.2 已否证「按 Activity 名判开屏」的可行性 |
| 6 | **广告 SDK 命名特征**：`vid*="skip"`、`vid*="count"&&vid*="down"`、`tt_splash_skip_btn` | 已在用（`BuiltInRules.VIEW_ID_SKIP`）；扩充需先采样 | 低，但会随 SDK 改版腐烂 | 【实测-本机】已有实现 |
| 7 | **点击后确认复用**（见 §2.3） | 已有能力 | — | 【实测-本机】 |

**共同代价（诚实说明）**：1/2/6 都是「经验特征」，**会随 App 改版腐烂**，需要持续采样与维护（对照 [业界调研与改进方案](业界调研与改进方案.md) §2.3：主流 App 的跳过按钮基本没有稳定 id/vid）。这部分成本是长期的、不可避免的。

### 2.2 `AccessibilityService.takeScreenshot`（Android 11 / 14 的截图能力）

#### 2.2.1 能力与硬约束（以官方源码与本地 SDK 元数据为准）

| 项 | 事实 | 证据等级 |
|----|------|---------|
| 元数据开关 | `android:canTakeScreenshot`，**since API 30** | 【实测-本机】`android-sdk/platforms/android-36/data/api-versions.xml` 中 `name="canTakeScreenshot" since="30"` |
| 取全屏截图 | `AccessibilityService.takeScreenshot(int displayId, Executor, TakeScreenshotCallback)`，**since API 30** | 【实测-本机】同上（`takeScreenshot(ILjava/util/concurrent/Executor;...)` since=30） |
| 取单个窗口截图 | `takeScreenshotOfWindow(int accessibilityWindowId, Executor, TakeScreenshotCallback)`，**since API 34**；官方 javadoc 明确推荐用于「目标窗口可能被无障碍悬浮窗遮挡」与「基于机器学习的视觉理解」场景 | 【官方源码】AOSP `core/java/android/accessibilityservice/AccessibilityService.java`（本次抓取 android14-release 分支核对） |
| 结果对象 | `AccessibilityService.ScreenshotResult`（since API 30）：提供 `HardwareBuffer` + `ColorSpace` + 时间戳；用 `Bitmap.wrapHardwareBuffer(buffer, colorSpace)` 构造 `Bitmap` → **不需要第三方图像库** | 【官方源码】同上 javadoc 原文；【实测-本机】api-versions.xml |
| 能力校验 | 服务没有该 capability 时抛 `SecurityException`：`AccessibilitySecurityPolicy.canTakeScreenshotLocked()` 实现为 `(service.getCapabilities() & CAPABILITY_CAN_TAKE_SCREENSHOT) != 0` | 【官方源码】AOSP `services/accessibility/java/com/android/server/accessibility/AccessibilitySecurityPolicy.java` |
| **系统级节流** | `AccessibilityService.ACCESSIBILITY_TAKE_SCREENSHOT_REQUEST_INTERVAL_TIMES_MS = 333`（@hide @TestApi），两次截图间隔 ≤333ms 直接返回 `ERROR_TAKE_SCREENSHOT_INTERVAL_TIME_SHORT` → **上限约 3 张/秒** | 【官方源码】AOSP `AccessibilityService.java` 常量定义 + `AbstractAccessibilityServiceConnection.takeScreenshot()` 的节流判定 |
| 其它失败码 | `ERROR_TAKE_SCREENSHOT_INTERNAL_ERROR`(1) / `NO_ACCESSIBILITY_ACCESS`(2) / `INTERVAL_TIME_SHORT`(3) / `INVALID_DISPLAY`(4) / `INVALID_WINDOW`(5) / **`SECURE_WINDOW`(6，Android 14 起)** | 【官方源码】AOSP `AccessibilityService.java` |
| 私有虚拟显示 | 类型为 `Display.TYPE_VIRTUAL` 且带 `FLAG_PRIVATE` 的显示不可截（返回 `INVALID_DISPLAY`） | 【官方源码】`AbstractAccessibilityServiceConnection.takeScreenshot()` |
| `FLAG_SECURE` 窗口 | 存在 `SECURE_WINDOW` 错误码（Android 14 起）→ 安全窗口内容不可截。【推断】其语义即「目标窗口/屏幕含 FLAG_SECURE」 | 【官方源码】错误码定义；【推断】具体触发条件 |
| 本项目现状 | `android:canTakeScreenshot="false"`（**当前关闭**）；`canPerformGestures="true"`；`minSdk=29`（**低于 API 30**） | 【实测-本机】`app/src/main/res/xml/accessibility_service_config.xml`、`app/build.gradle.kts` |

**minSdk 29 的适配后果**：截图 API 与属性都是 API 30+，在 Android 10（API 29）设备上不可用，代码必须用 `Build.VERSION.SDK_INT >= 30` 守卫，UI 也要区分「本机不支持」。【推断，基于上面的 since 数据】

#### 2.2.2 开启 `canTakeScreenshot` 的系统权限提示与用户感知

- **AOSP 层面没有额外确认流程**：`core/res/res/values/attrs.xml` 里 `<attr name="canTakeScreenshot" format="boolean" />` 只是布尔属性；运行时只有「capability 是否声明」的检查（见上表）。**本地可证的否定性结论：AOSP 中没有为截图能力单独弹窗/二次确认的代码路径。**
  【官方源码】AOSP `core/res/res/values/attrs.xml`、`AccessibilitySecurityPolicy.java`
- **用户能感知的部分**：截图能力声明在服务的 meta-data 里，用户可以在系统「无障碍 → 该服务」页面看到服务信息；具体文案由系统/ROM 决定。【推断】
- ⚠️ **HyperOS（本机小米 14）是否额外提示、是否静默降级或限制截图：未知**，必须真机验证（本次未做）。
- ⚠️ 若未来上架 Google Play，无障碍 API 的使用需符合其政策声明要求（本次**未取到**该政策页面，标记为【未知】）。

#### 2.2.3 隐私影响

- 截图拿到的是**整屏位图**，包含用户当前屏幕上的一切内容（聊天、通讯录、表单、他人信息）。`FLAG_SECURE` 窗口除外，但普通 App 默认不开 `FLAG_SECURE`。
- 与项目现状的关系：本项目当前隐私约定是「屏幕内容相关能力必须本地处理、不上传」（见 [业界调研与改进方案](业界调研与改进方案.md) §6）。**截屏本身仍全部在本地**，但：
  1. 它显著扩大了「App 能看到的屏幕内容范围」（从「无障碍树里的文本」扩大到「整屏像素」）；
  2. 因此**是否需要新增隐私告知/开关、是否默认关闭**，属**产品决策**（见 §5），本文不代替决定。
- 建议的安全约束（若实施）：只在「开屏窗口内 + 已判定为像素渲染类页面 + 用户显式开启」时截图；截完立即回收 Bitmap，不落盘、不入库（现有快照功能是把无障碍树写盘，**不要让截图混入同一条路径**）。

#### 2.2.4 性能（算术推算，非实测）

- 单帧内存：1080×2400×4 字节 ≈ **9.9 MiB/帧**（1080×2400×4 = 10,368,000 B）。【实测-本机】算术推算，可在本地复核
- 按系统节流的理论上限（3 帧/秒）连续截图 ≈ **30 MiB/s 量级的像素拷贝流量** + 后续分析开销 → 对内存带宽、GC、发热都有压力。【推断】
- 缓解方向（都需实测确认）：①按需单帧而非连续 ②先 `Bitmap.createScaledBitmap` 降采样到 1/4 再分析 ③复用与及时 `recycle()` ④把帧间差分控制在「只在窗口内、最多 N 帧」。
- **真实的帧率/内存/耗电影响：未实测，未知。**

#### 2.2.5 不引入第三方库能做哪些「简单像素启发式」

工具就是 `android.graphics.Bitmap` + 手写数组循环（系统的 `Color`/`Bitmap.getPixels`），**不需要 OpenCV**。【推断】

| 启发式 | 思路 | 成本 | 风险 |
|--------|------|------|------|
| **A. 右上角高对比小块** | 截取右上角固定区域（如 W×0.35 / H×0.12），转灰度 → 阈值二值化 → 连通域 → 找面积在 [下限, 上限] 且与背景对比明显的块 | 需手写连通域标记（中等） | 深色/浅色主题、视频广告、角标会干扰；阈值需按 App 调 |
| **B. 倒计时数字区域变化** | 对同一区域做**帧间差分**：相邻两帧差异像素占比超阈值的连通块 → 其变化周期 ≈1 秒的区域即倒计时 | 需要至少 2~3 帧（受 333ms 节流限制，约 1 秒能拿 3 帧） | 视频广告整屏都在变 → 差分失效；需要配合 A 的区域先验 |
| **C. 全局变化块定位** | 全屏帧间差分，取「变化集中且面积小」的块作为候选 | 同上 | 同上 |
| **D. 采样降分辨率** | 先降到 1/4 再做 A/B | 低 | 小字号倒计时可能被降采样抹掉 |

**这些启发式的命中率与误点率全部未实测**；能确定的是「技术上不需要第三方库就能实现」，以及「系统给了 333ms 的节流上限」。

| 折中方向（**也需产品决策**） | 只上传**裁剪后的按钮候选小图**（而非全屏），配合本地先验定位候选区域；但这仍然是「数据出本地」 | 【推断】 |
| 成本 | 服务端调用费用、流量、以及为降低延迟可能需要的常驻连接 | 【推断】 |

## 4. 方案对比矩阵 + 三种取舍

### 4.1 对比矩阵

| 维度 | **A：不引入第三方**（弱信号启发式 + 截图启发式 + 坐标候选） | **B：仅引入宽松许可端侧 OCR**（Tesseract 或 PP-OCRv5-mobile + 宽松许可运行时） | **C：引入更强模型**（ML Kit 闭源 / YOLO 检测 / 云端） |
|------|------------------------------------------------|--------------------------------------------------|---------------------------------------------|
| 是否破「零第三方业务依赖」 | **否** | **是**（库 + 模型文件） | **是**（且可能是闭源二进制 / AGPL / 云服务） |
| 许可风险 | 无 | 低（Apache-2.0 / MIT / BSD-3-Clause） | 中~高（ML Kit 闭源条款或 GMS 依赖 / Ultralytics AGPL-3.0 / 数据出境） |
| 包体增量（外部来源，未复现） | **0** | 低档：Tesseract chi_sim fast ≈2.35 MiB（+ native 未知）／高档：PP-OCRv5 det+rec ≈20.7 MB、ORT AAR ≈26.6 MiB、LiteRT ≈7.3 MiB | ML Kit 捆绑 +≈4 MB/脚本/架构；YOLO 检测器 ≈5 MB（二手）；ncnn 全 ABI 包 20~31 MiB（二手/元数据） |
| 精度量级 | **未知**（取决于像素启发式，无任何实测） | **未知**（官方 OCR 指标不可外推到「跳过按钮识别率」） | 二手：19/20 命中、0 误点（未复现） |
| CPU/内存/耗电 | 截图 ≈9.9 MiB/帧（推算）+ 自研图像处理（未知） | 未知（官方 CPU 数字非手机平台） | VLM 级单次 2~4 秒（二手），可能与开屏窗口不匹配 |
| 离线能力 | 完全离线 | 完全离线 | ML Kit 捆绑离线 / YOLO 离线 / **云端不在线不可用** |
| 隐私 | 屏幕内容仅在本机 | 屏幕内容仅在本机 | ML Kit 官方称本地；云端 = **数据出本地** |
| 维护成本 | 需自研图像处理；阈值与坐标会随 App 改版腐烂 | 需引入/裁剪运行时 + native 构建 + 模型更新 | ML Kit 最低（托管）↔ 自训模型最高（数据+训练+评测） |
| 覆盖率上限（**推断**） | 中（只覆盖规律性强的按钮） | 高（页面上有文字就能读） | 最高（纯图形按钮/倒计时圆环） |
| 误点风险 | 中（坐标/像素误判） | 中（OCR 误读「跳过/关闭/×」） | 中~低（取决于模型与负样本） |
| 决定性前提 | 接受开启截图能力 + 接受自研图像处理 + 接受长期调参 | 项目允许新增第三方库 + 接受包体 +N MB + 接受 native 构建维护 | 有 GMS（ML Kit）／接受 AGPL 或购买 Enterprise 授权／接受数据出境 |

### 4.2 三种取舍的代价与适用前提（**不含推荐**）

**取舍 A：完全不引入第三方**
- 能做什么：§2.1 弱信号规则、§2.2 截图像素启发式、§2.3 坐标候选 + 复核。
- 代价：①需要开启 `canTakeScreenshot`（扩大服务能力，见 §2.2.2）；②图像处理要自研（无 OpenCV），阈值调参是长期工作；③对「纯图形按钮 + 无规律位置」的广告，理论上限就是「猜得准的坐标先验」，**覆盖率存在天花板**。
- 适用前提：产品接受「部分 App 仍然跳不过」，且接受截图能力与自研图像处理的人力。

**取舍 B：只引入宽松许可的端侧 OCR**
- 能做什么：把「有文字但无障碍树读不到」的页面（D 类中的一部分）覆盖掉；也可只对候选小图做 OCR。
- 代价：①破「零第三方业务依赖」；②包体 +N MB（档位从 ≈2.35 MiB 到 ≈20.7 MB 不等，且 native 库体积未知）；③需要 JNI/native 构建（Tesseract 在 Maven Central 检索不到）或额外的运行时（ORT/LiteRT/ncnn）；④OCR 精度在本场景**未知**，需要真机标定集评测。
- 适用前提：有明确的包体预算上限、能承担 native 构建与长期模型维护。

**取舍 C：引入更强模型（闭源 / AGPL / 云端）**
- 能做什么：纯图形按钮、倒计时圆环这类最难场景，是业界（ad-skipper）唯一做到高命中的路线。
- 代价：①ML Kit 需 GMS 且是闭源二进制（国行设备前提未验证）；②Ultralytics YOLO 是 AGPL-3.0，商业部署边界需法务判断；③云端方案与「数据不出本地」直接冲突；④自训模型需要数据与训练管线（本项目当前没有）。
- 适用前提：产品/法务先给出许可与隐私结论，且接受包体与合规成本。

## 6. 最小可行落地路径（若产品选择「引入」，按阶段推进）

> 每阶段都给：目标 / 改动面 / 验收指标 / 退出（回滚）条件。
> ⚠️ 下面所有「建议阈值」均是**建议初值（推断）**，具体数值应由产品按 §5 决策后给定。

### 阶段 0：判定与埋点（零风险，先做）

- **目标**：把「跳不过的 App」按 §1.2 判定表分成 A/B/C/D/E 类，得到**真实基线**（当前无任何兜底层的命中率数据）。
- **改动面**：只加埋点与采集，不改跳过逻辑。
  - 采集：规则页「页面快照」→ `files/snapshots/`（`app/src/main/java/com/bsfeng/monitor/skip/SnapshotExporter.kt`、`app/src/main/java/com/bsfeng/monitor/skip/SnapshotRequest.kt`）
  - 埋点：`app/src/main/java/com/bsfeng/monitor/util/DiagnosticCounters.kt` + 跳过事件 `app/src/main/java/com/bsfeng/monitor/skip/SkipEventRecorder.kt`
- **验收指标**：①N 个目标 App 有分类结论（N 由产品定）；②埋点能区分「未命中规则」/「命中但复核失败」；③快照里能看到 D 类特征（Surface/单 View/无文本）。
- **退出条件**：若分类结果显示 D 类占比极低（即绝大多数「跳不过」其实是 A/B 类规则没写好），则**兜底层不需要做**，回到 P2-1 规则调优。

### 阶段 1：弱信号启发式（零依赖，不改引擎）

- **目标**：用 §2.1 的弱信号把 C 类里的「小块可点击 + 右上角 + 叶子节点」覆盖掉。
- **改动面**：`app/src/main/java/com/bsfeng/monitor/skip/BuiltInRules.kt`（新增规则 + 递增 `BUILT_IN_VERSION`）；必要时在规则页做开关。引擎不改。
- **验收指标**：①目标 App 开屏命中（`AD_SKIPPED` 记录的 `selector` 非空且可读）；②`confirmed=true` 比例；③正常页面零误点（`AD_SKIPPED` 逐条可追溯到 selector，与业界调研 §5 的验收口径一致）。
- **退出条件**：若新规则在正常页面产生误点记录（`confirmed=false` 且用户手动返回），立即回滚该规则。

### 阶段 2：截图启发式（零依赖，但要开能力）

- **目标**：覆盖 D 类（像素渲染页）中的「右上角固定位置有跳转/倒计时按钮」场景。
- **改动面**：
  - `app/src/main/res/xml/accessibility_service_config.xml`（`canTakeScreenshot="true"`，并按 Q2 决定是否加 UI 开关）
  - 引擎侧新增截图调度与像素分析（**建议新文件**，不要塞进 `SkipRuleEngine.kt`；注意与 300ms 扫描节奏、`VERIFY_DELAYS` 复核期的交互）
  - 点击复用 `app/src/main/java/com/bsfeng/monitor/skip/ActionExecutor.kt` 的 `clickAt`
- **必须实测的指标**（当前全部未知）：①候选定位命中率；②误点率；③单帧截图往返耗时；④连续截图时的内存峰值与 GC；⑤耗电（建议用系统电池统计做前后对比，本次未做）；⑥Android 10（API 29）设备上的降级行为。
- **退出条件**：误点率超过 Q5 的阈值 → 先收紧区域/帧数，仍超则关闭该层（保留开关默认关）。

### 阶段 3：OCR（**必须先通过 Q1/Q3/Q4 决策**）

- **目标**：覆盖「有文字但无障碍树读不到」的页面。
- **改动面**：按所选技术栈新增依赖（`app/build.gradle.kts`）+ 推理封装；**建议只对候选小图做 OCR**（降低耗时与隐私面），而不是整屏。
- **验收指标**：①候选区域 OCR 文本命中率（需自建小规模标定集）；②单次耗时；③包体增量实测值（对照 Q4 的上限）；④隐私告知已上线（Q3）。
- **退出条件**：包体或耗时超出 Q4/Q6 上限 → 降级到更小模型档位或回退阶段 2。

### 埋点建议（各阶段通用）

| 字段 | 含义 | 建议落点 |
|------|------|---------|
| `layer` | 命中层级：`l1_node` / `l2_weak_signal` / `l3_screenshot` / `l4_ocr` | `AD_SKIPPED.detail`（经 `SkipEventRecorder`） |
| `pageClass` | 页面分类：A/B/C/D/E | `AD_SKIPPED.detail` |
| `candidateRect` | 候选点击区域（屏幕坐标 + 归一化） | `AD_SKIPPED.detail`（坐标先验的唯一来源） |
| `shotMs` / `analysisMs` / `ocrMs` | 各阶段耗时 | `DiagnosticCounters` |
| `confirmed` | 已有（`true/false/null`） | 已落 `AD_SKIPPED.detail.confirmed` |
| `frameCount` | 单次开屏的截图帧数 | `DiagnosticCounters` |

### 9.2 已知风险

1. **预设前提被证伪的风险**：本次核实发现「Flutter/Unity/WebView 一定无文本」**不成立**（三者都可能带文本），如果按错误前提直接上 OCR，可能投入了成本却解决了一个本来靠规则调优就能解决的问题 → 必须先做阶段 0。
2. **截图能力的合规与用户信任风险**：开启 `canTakeScreenshot` 会扩大 App 能看到的内容范围；虽全本地处理，但需告知与开关（Q2/Q3）。
3. **包体与 native 构建风险**：任何 OCR/推理框架都带来 native 构建、ABI 裁剪、模型分发的新维护面；Tesseract 在 Maven Central 检索不到，集成路径更长。
4. **许可风险**：Ultralytics AGPL-3.0 是明确的法律风险点；ML Kit 是闭源二进制（禁止逆向）；二者都不是「拿来做就完了」的选择。
5. **精度数字不可直接外推**：PaddleOCR 的 81.29%、ad-skipper 的 19/20 都是各自场景的指标，**不能**作为「本项目跳过按钮识别率」的预期。
6. **规则/坐标长期腐烂**：§2.1 与 §2.3 的方案都会随 App 改版失效，需要持续采样维护——这是持续成本，不是一次性投入。
7. **系统节流是硬上限**：333ms 间隔（≈3 帧/秒）意味着任何「连续视频流式分析」的方案在无障碍截图路径上都不可行。
8. **API 29 设备降级**：minSdk 29 低于截图 API 的 30，需明确「老设备不支持兜底层」的降级行为。
