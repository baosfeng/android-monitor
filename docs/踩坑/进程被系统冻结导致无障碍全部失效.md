# 踩坑：进程被系统冻结导致无障碍「全部」失效

> ⚠️ **何时阅读：** 用户反馈「广告跳不过」「记账不弹窗」**同时**出现，或任何「服务已开启但什么都不工作」的场景。

## 一句话结论

不是规则、不是 H5、不是代码回归，而是**应用进程被 MIUI/HyperOS 冻结（`cgroup.freeze=1`）**，
`onAccessibilityEvent` 不再投递，广告跳过与自动记账**一起**失效。

## 现象

| 观察 | 值 |
|---|---|
| 设置页无障碍状态 | ✅ 显示已开启 |
| `settings get secure enabled_accessibility_services` | 含 `SelectToSpeakService` |
| `dumpsys accessibility` → Enabled services | 含本服务 |
| 广告跳过 | ❌ 无反应 |
| 自动记账 | ❌ 不弹窗 |
| `logcat` 里 `MonitorDebug` / `MonitorTimeline` | **一条都没有** |

「配置全对、日志全空」是这个坑的**唯一识别特征**：进程没在跑，所以没有任何输出。

## 根因

进程被系统放进冻结 cgroup，线程被挂起：

```bash
PID=$(adb shell pidof com.bsfeng.monitor)
adb shell cat /sys/fs/cgroup/apps/uid_10278/pid_$PID/cgroup.freeze   # → 1 = 已冻结
adb shell cat /sys/fs/cgroup/apps/uid_10278/pid_$PID/cgroup.events   # → frozen 1
adb shell cat /proc/$PID/stat | awk '{print $14, $15}'               # utime/stime 不再增长
```

冻结与「无障碍授权」是两件事：授权仍有效、服务仍显示 Bound，但**进程不执行任何代码**，
因此事件回调、`AlarmReceiver` 心跳、轮询全部停摆。

## 判定：三个计数器互相矛盾

真机（小米 14 / HyperOS / Android 16，2026-10-22）实测：

| 判定面 | 读数 | 说明 |
|---|---|---|
| `enabled_accessibility_services` | 有本服务 | 用户勾选态，**冻结时仍是正常值** |
| `dumpsys accessibility` Bound services | `label=行为记录` | 绑定关系还在，**不代表进程在跑** |
| `/proc/<pid>/stat` 的 utime/stime | 5 秒内**零增长** | ✅ 进程真的没在运行 |
| `cgroup.freeze` | `1` | ✅ 定性为冻结 |

**只看前两行会误判为「一切正常」**，必须看进程级指标。

## 解冻与验证

```bash
# 拉起自己（不要 force-stop，见 MIUI-force-stop 踩坑）
~/android-platform-tools/adb shell am start -n com.bsfeng.monitor/.MainActivity
adb shell cat /sys/fs/cgroup/apps/uid_10278/pid_$PID/cgroup.freeze   # → 0
adb shell cat /proc/$PID/stat | awk '{print $14, $15}'              # → 开始增长
```

解冻后立刻冷启动闲鱼，引擎日志恢复且**广告正常跳过**：

```
SkipEngine: 进入 App com.taobao.idlefish / com.taobao.fleamarket.splashad.SplashAdDialog
SkipAction: CLICK: ACTION_CLICK 成功
SkipRecorder: 记录跳过事件: 闲鱼 (com.taobao.idlefish)（已确认）
```

同一份代码、同一套规则、同一个 App —— 冻结时零输出，解冻后一次命中。
**这就是「以前能跳、现在不能」的全部差异。**

## 为什么现有保活没挡住

| 机制 | 位置 | 为什么无效 |
|---|---|---|
| `AlarmManager.setInexactRepeating` 60s 心跳 | `service/AlarmReceiver.kt:101` | 非精确闹钟，冻结/Doze 下可被无限推迟；且**回调要进程能跑**，冻结时连广播都收不到 |
| `HealthChecker.isAccessibilityServiceRunning` | `service/HealthChecker.kt:37` | 查的是 `getEnabledAccessibilityServiceList`（勾选态），**冻结时仍返回 true** → 判定为健康，不告警 |
| `AccessibilityStatus.isEnabled` | `util/AccessibilityStatus.kt:40` | 同理，`serviceRunning \|\| 勾选态 \|\| Manager 列表`，三项在冻结时都可能为真 |
| 设置页「忽略电池优化」 | `ui/SettingsScreen.kt:580` | 只跳系统列表页（`ACTION_IGNORE_BATTERY_OPTIMIZATION_SETTINGS`），需用户手动勾选；清单未申请 `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`，无法直接弹授权 |

结论：**当前所有健康判定都停在「授权/绑定」层，没有一条能看见「进程是否真在跑」。**

## 已落地：心跳活性检测（1 + 2）

`service/HeartbeatWatchdog.kt`：前台轮询链每 1 秒写一次 `elapsedRealtime()`（`monitor_prefs` 的
`heartbeat_last_ms`）。判定核心是纯函数 `isStale(last, now, 3min)`，阈值 `STALE_THRESHOLD_MS` = 3 分钟。

**关键取舍：记录「历史中断」而不是「此刻是否停更」。** 冻结只能被用户打开 App 发现，而打开 App
这个动作本身就会解冻进程 —— 只判当下的停更状态，设置页永远显示正常，等于没做。因此心跳恢复时
回看与上次的间隔，超阈值就记一条中断（`heartbeat_gap_ms` + `heartbeat_gap_recovered_at`），
由设置页展示「上次监控中断约 12 分钟（22:08 恢复）」，并给「去关闭」按钮直达本应用信息页
（省电策略 / 自启动都在那一页）。

`HealthChecker` 另有一条兜底：广播还能收到、但服务已长时间没 tick 时推「监控进程疑似被冻结」通知。

边界（按代码口径）：
- `onServiceStopped()` 在 `onDestroy` 清掉心跳 —— 用户自己关服务不会被误报成冻结；
- 从未记录（新装）与 `now < last`（设备刚重启、`elapsedRealtime` 归零）都不判中断；
- 进程被杀后重启会留下同样间隔，语义上同属「监控中断过」，一并提示。

剩余可做（收益递减）：心跳改 `setExactAndAllowWhileIdle`（Doze 下也能唤醒，代价是耗电与精确闹钟配额）。

## 教训

**「功能不工作」要先去进程层看一眼，再怀疑代码。** 本次在规则、选择器、H5、窗口架构上排查了很久，
实际答案是进程根本没运行。判定顺序推荐：

1. `logcat | grep MonitorDebug` 有没有输出（无输出 → 进程级问题，别读业务代码）
2. `/proc/<pid>/stat` 的 utime/stime 是否增长（不增长 → 冻结/挂起）
3. `cgroup.freeze` 是否为 1（定性）
4. 以上都正常，才进入规则与选择器层排查

[第三方悬浮窗顶掉根窗口](第三方悬浮窗顶掉无障碍根窗口.md)。
